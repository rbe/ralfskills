# Requirements of release

The rows that the skill `release` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-57"></a>R-57 | Release ships the slice | in force | `release` ships a reviewed slice. It stops when `make lint` or `make test` failed or did not run, or when a finding is neither fixed nor a roadmap row. `release` asks the owner before the ship when the request did not ask for one. That is the only question: the merge through `make pull-request-merge WAIT=1` or a Git merge commit asks the owner nothing. When the owner merges later, `release` does every step before the merge. The slice is one branch. `release` commits the change and pushes the branch. The first line of a commit message is one sentence that says what the system now does. CI runs the same Make targets on that push. `release` runs `make ci-status WAIT=1`, and it stops when the target fails, because the run failed, did not finish, or does not exist. A repository with no workflow runs the same six gate targets on the machine instead. When the gates passed, `release` writes the Release section, asks `record` to close the task, and commits the board documents on the same branch, so the board is correct on the default branch after the merge. Then `release` merges the branch into the default branch and pushes the default branch. If `.github/workflows` exists and `make help` lists `pull-request`, `release` runs `make pull-request` and `make pull-request-merge WAIT=1`. If not, it makes a Git merge commit. The owner creates a `v*` tag. A skill creates none. A push to the default branch publishes when `github-pipeline` is installed. A shipment is a binary, a container image, or a library package. A Make-only repository then runs the target its `CLAUDE.md` names, such as `make build` for a library package. A library with no package ships with the merge. This applies to a product repository, and to this collection without the publish. `release` owns the steps. |
