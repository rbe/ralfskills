# Requirements of record

The rows that the skill `record` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-4"></a>R-4 | Skill name matches directory | in force | The `name` in a skill's frontmatter matches its directory. `make toon` reads every `SKILL.md` in the installed set and fails when a name does not match. This applies to this collection and to every installed skill. `record` owns the check. |
| <a id="r-65"></a>R-65 | Frontmatter is YAML | in force | APM reads the frontmatter of a `SKILL.md` as YAML and refuses to install a collection when one skill does not parse. A frontmatter value is one YAML string. It has no colon followed by a space and no ` #`, or it is quoted. `make toon` fails when a value breaks this rule. The APM install of this collection into a sample project is the check that the collection installs. This applies to this collection and to a product skill. `record` owns the check. |
| <a id="r-20"></a>R-20 | record writes ids and documents | in force | `record` is the only writer of ids and of board documents. A stage calls `record` by name before any id or any document. A write that skips `record` fails that step. `record` does not delegate the id check to another skill. Close mode stops when the Plan, Develop, or Review section still reads `Not invoked yet.`. Write mode rejects a history file that misses one of the four headings Plan, Develop, Review, and Release. A skill that is not a stage adds one line that names the skill to the section of the stage that runs, so a language skill adds its line under Develop. Such a skill opens no history file, and it adds no line when no history file is open. `record` states this rule once, and no other skill repeats it. This applies to both. `record` owns the write. |
| <a id="r-24"></a>R-24 | Product document homes | in force | A product repository keeps five homes, and `record` is the only writer. The things to do are the rows of `docs/ROADMAP.md`, one table with the columns id, kind, title, and proposal. The kind is feature, defect, or question. The id has the form `W-` plus a number. The table has no status column, because a row in the table is not done. `record` deletes the row when the slice closes. The detailed plan of one roadmap row is `docs/proposals/<id>.md`, with an id of `P-` plus a number. A rule in force is an ADR, `docs/adr/<id>.md`, with an id of `ADR-` plus four digits, or a row of a file in `docs/requirements/`. The report of one slice is `docs/history/<id>.md`, with an id of `H-` plus the date and a slug. The history file is complete at any time, and it holds nothing that waits for a decision or for work. The code and the tests are the current state. `plan` reads these before it asks. There is no `docs/DECISIONS.md` and no `docs/KNOWN_ISSUES.md`. When a repository has ADR files, `make toon` and `make project-report` keep that product behaviour. `plan` and `migrate-docs` name the roadmap path and the ADR path. This applies to a product repository. `record` owns the files. |
| <a id="r-67"></a>R-67 | Board templates | in force | `record` has one template for each board document in `templates/`: `ROADMAP.md`, `adr.md`, `proposal.md`, and `history.md`. `record` copies the template at the first write and keeps its layout. The first ids are `W-1`, `P-1`, and `ADR-0001`. The branch of the slice has the slug of the history id as its name, as in `H-2026-11-20-slugify`. An ADR, a proposal, and a history file have a frontmatter block. A list in the frontmatter is on one line and holds ids only. The roadmap is a table with the columns Id, Kind, Title, and Proposal. The scripts of `record` and `project-report` read these layouts and no other. When `record` creates a history file, it sets `roadmap:` to the roadmap row of the task, and it adds that row when the task has none. The next number of a kind comes from `make id KIND=<kind>`, which raises the counter of that kind in `docs/ids.yaml` by one, as [R-13](#r-13) says. In an ADR, `skills` names installed skills. A rule for every change names `develop` and `review`. This applies to a product repository. `record` owns the templates. |
| <a id="r-53"></a>R-53 | Where a choice that must hold goes | in force | When the owner answers a choice that must hold, `plan` asks `record` where it goes. `record` decides in this order: a small requirement, which is a row of the file of its owner in `docs/requirements/` where the repository keeps those files; a sentence in an ADR that fits; a new ADR. `record` writes a new ADR with the status `Accepted`, and the Plan section cites that id. If no home fits, the agent asks the user. Not every choice is a rule, and a choice that need not hold has no home. A repository that keeps `docs/requirements/` and no `docs/adr/` has only the first home. This applies to both. `plan` owns the request. `record` owns the write and the place. |
| <a id="r-55"></a>R-55 | An ADR may replace a skill rule | in force | An accepted ADR replaces a skill rule only when the ADR is a divergence. A divergence names the rule, what differs, and why. An ADR that differs from a skill rule and does not name these three is a finding in `review`. What `github-pipeline` says is not a divergence stays not allowed. A pipeline divergence is written where `github-pipeline` says. Every other divergence is an ADR. This applies to a product repository. `record` owns the rule. `review` owns the check. |
| <a id="r-56"></a>R-56 | ADR status and replacement | in force | `record` owns the ADR status. The values are `Accepted` and `Superseded`. A new ADR names the ADR it replaces in `supersedes`. `record` then sets the status of the replaced ADR to `Superseded`. `plan`, `develop`, and `review` follow only an accepted ADR. The project report does not list a superseded ADR as an id with no test. This applies to a product repository. `record` owns the status. |
| <a id="r-61"></a>R-61 | ADR body | in force | An ADR body has the section `## Rule` and the section `## Why`. Rule is what an agent must do or must not do, in sentences `review` can check. Why is the reason, and the options that were not chosen. An ADR that replaces a skill rule also has the section `## Divergence`. An ADR is short. It does not copy the grill. This applies to a product repository. `record` owns the sections. |
| <a id="r-26"></a>R-26 | Four history sections | in force | Every history file has the headings Plan, Develop, Review, and Release. `record` rejects a file that is missing one. [R-25](plan.md#r-25) and [R-59](develop.md#r-59) say who creates the file. The status of a history file is `started` or `closed`. Later stages append. A stage that did not run gets one sentence. Plan holds the questions and answers when `plan` ran. Develop holds what changed and which language skill was used. While the task is open and `develop` has not run, Develop is `Not invoked yet.` When the task closes or waits, that section is one sentence. Review holds the gates, the subskill results, the findings, and what was left alone. A subskill that is not installed is one line, as [R-30](plan.md#r-30) says. Release holds what shipped, or `Not invoked: this slice does not ship.`, or `Not invoked yet.` An agent on another task opens a history file only when an id names it. A history file is a report: it holds what was done, what was found, and what was not run, each as a fact. It is complete at every stage end and is not rewritten when a row is deleted later. A declined idea is a fact of the history file of its slice, written in Plan as `Declined: <idea>, because <reason>.`, and no other document keeps it. An item that waits for work or for a decision goes to a roadmap row, or to a planned row of a file in `docs/requirements/`, and the history file may name that id. This applies to a product repository. `record` owns the headings. Each stage owns its section. |
| <a id="r-58"></a>R-58 | Closing a task | in force | `release` asks `record` to close the task, when the slice shipped and when it does not ship. A task whose work waits stays open. A slice that is done and waits only for the merge of the owner is closed on its branch. `record` stops when the Plan, the Develop, or the Review section of the history file is still `Not invoked yet.` `release` writes the Release section before it asks for the close. `record` sets the history status to `closed`. It deletes each roadmap row that `roadmap:` of the history file names, and retires its id. A defect and a question are roadmap rows too. It stops when a test still names a retired roadmap id. It sets the status of the proposal to `done`. The status of a proposal is `open`, `started`, or `done`. An ADR and a requirement row stay in force. In a repository that keeps `docs/requirements/` and does not keep `docs/ROADMAP.md`, `record` turns the planned row of the task to in force, or deletes it and retires its id when the task left no rule. This applies to both. `record` owns the steps. |
| <a id="r-27"></a>R-27 | Links are id keys | in force | An ADR, a proposal, and a history file name other documents by id. The YAML keys are `id`, `title`, `status`, `adrs`, `skills`, `roadmap`, `proposals`, and `supersedes`. A history file written before the roadmap table may have the keys `decisions` and `issues`, and `make ids` reads them like any other list. The key `relates:` is not used. A list key holds ids only, as [R-13](#r-13) says. In the frontmatter and in the id cell of a table, the scripts read an id as plain text, as [R-69](#r-69) says. A test does not put the id in a path. An id in a path fails `review`. This applies to a product repository. `record` owns the keys. This collection's rules are rows of the files in `docs/requirements/`, as [R-28](#r-28) says, and do not use this YAML block. |
| <a id="r-69"></a>R-69 | Ids are links | in force | In running text of a document under `docs/`, each id is a link to its item, so a person goes from one item to the other with one click. `make links` writes the links. An agent writes the plain id and runs the target. A table row gets an anchor in its id cell, and the anchor is the id in lowercase. An id of a table row links to that row. An id of an ADR, a proposal, or a history file links to that file. `make links-check` fails when an id in running text is not a link, when a link is wrong, or when a row has no anchor. `review` runs it. `make project-report` gives each item an anchor and links each id, with a path from `build/`. This applies to both. `record` owns the two targets. |
| <a id="r-13"></a>R-13 | Ids are never reused | in force | `record` issues every id. `docs/ids.yaml` holds one counter for each kind of id that has a number, as one line `R: 83`. The counter is the highest number issued. `make id KIND=<kind>` prints the next id of that kind, raises its counter by one, and creates the file when it does not exist. `make id-raise KIND=<kind> TO=<number>` sets a counter to a higher number, for a repository that already uses ids of that kind. The counter only grows, so a number is never issued twice, also after its row or file is deleted. A deleted row is gone. No list of retired ids and no map of merged ids exists, and `make ids-retire` does not exist. An id is valid when its number is not above the counter of its kind, so a history file that names the id of a deleted row stays valid. A history id, `H-` plus a date and a slug, has no counter and must be unique among the files. `make ids` reads the id cell of each row in the files of `docs/requirements/` and in `docs/ROADMAP.md`, every `id:` line in a Markdown or YAML file under `docs/`, and `docs/ids.yaml`. It exits non-zero on a line of `docs/ids.yaml` that is not a counter, on a list item that is not an id, on an id above its counter, on the same live id twice, on a counter below the highest live id of its kind, and on a file `docs/REQUIREMENTS.md`, which the files of `docs/requirements/` replace, and `record` then does not write the document. A frontmatter list of ids is written as `[a, b]` on one line, and an empty list is `[]`. A list holds ids only, never text and never a bare id. The caller does not invent an id in prose. This applies to both. On this collection the ids are requirement rows. On a product repository they are the ids in [R-24](#r-24). `record` owns issuance. |
| <a id="r-6"></a>R-6 | Generated TOON indexes | in force | `make toon` writes the ADR index and the skill index through `$(PYTHON)`. Hand-editing a generated index is a defect. Run `make toon` after a skill is installed or removed, after ADR frontmatter changes, after a file of `docs/requirements/` changes, and before `plan`, `develop`, or `review` reads an index. `make setup` runs `toon` when the include is present, after `doctor` as [R-73](project-setup.md#r-73) says. `project.mk` and `sdlc.mk` include `.claude/skills/record/index.mk`. The ADR index is `docs/adr/index.toon`. `plan` opens one ADR when the id matches. The skill index is `docs/skill-index.toon`. It lists installed skills whose frontmatter `kind` is `language` or `check`. In a product repository the installed set is `.claude/skills/`. In this collection, before install, it is `skills/`. A language row sets `files` to extensions and `names` to exact filenames such as `Makefile`. A check row sets `order`. When the repository keeps `docs/requirements/` and has no ADR file, `make toon` writes `docs/requirements-index.toon`, still writes the skill index, and does not create `docs/adr/`. The status is `planned` or `in force`, so an agent that reads the index sees which rows are open work. This applies to both, with that switch. `record` owns the target. |
| <a id="r-28"></a>R-28 | This collection's board | in force | This collection is not a product repository. It has no `docs/ROADMAP.md` and no `docs/adr/`. Each rule is one row of a table in `docs/requirements/<skill>.md`, with the columns Id, Title, Status, and Statement. The file is the one of the skill that owns the row. The owner of a row is the skill of its sentence `<skill> owns ...`. A row with several owners stands in the file of the skill whose rule it mainly states. A row with no owning skill stands in `docs/requirements/collection.md`. A planned row stays in the file of its owner. The ids are global, and a row keeps its id when it moves to another file. There is no `docs/REQUIREMENTS.md`. The status is `planned` or `in force`. A planned row is the open work or the open question of the collection, and its statement names the choices of a question. An in force row is a rule that holds. A task that closes turns its row to in force, or deletes it. A choice that must hold is a row, as [R-53](#r-53) says. This collection has no `docs/DECISIONS.md` and no `docs/KNOWN_ISSUES.md`. The files of `docs/requirements/` replace `docs/adr/` and `docs/ROADMAP.md` here. `make req` reads one row, as [R-84](#r-84) says. This collection keeps no test on skill wording. The unit tests cover the scripts and the makefiles. A unit test also checks the shape of each `SKILL.md`, as [R-76](project-setup.md#r-76) says, and a string that a script or another skill reads. Each unit test names the requirement id with `id:` in its header. A task closes as [R-58](#r-58) says. [R-6](#r-6) and [R-3](project-report.md#r-3) say what `make toon` and `make project-report` do when there are no ADR files. This applies to this collection. `record` owns the distinction. |
| <a id="r-1"></a>R-1 | Tests name a requirement | in force | A test names the requirement it proves with `id:` in its header or metadata. That is the line `record` matches. The test name states what the system does when that requirement holds. A test with no id fails `develop` and fails `review`. On a product repository the id is an ADR id or the id of a requirement row in force. A roadmap row is work, not a rule. Its id is retired when the work ends, so a test does not name it. A planned row is not in force, so a test does not name it either. A test for a fixed defect names the ADR or the requirement row that states the fixed behaviour. An existing test with no id gets a requirement row that states the behaviour it proves. On this collection, where `docs/requirements/` is kept and `docs/adr/` is not, the id is an in force row of a file there. `project-setup` asks `record` where the behaviour of an existing test with no id goes, as a requirement row or an ADR. `project-report` fails the target when a test has no id. [R-63](project-report.md#r-63) says where the line is in each language. This applies to both. `develop` and `review` own the stop. `record` owns the matching line. |
| <a id="r-84"></a>R-84 | make req reads one row | in force | `make req` prints the requirement rows and the ADRs that a question needs, so that an agent reads one row and not a whole file. `make req ID=R-45` prints that row, and `ID="R-45 R-75"` prints each. `make req Q=<word>` prints id, title, and file of each item whose title or statement holds the word, in any case, and `FULL=1` adds the statement. `make req OWNER=<skill>` lists the rows of one owner, and `make req STATUS=planned` lists the rows with that status. A filter combines with the others, an `ID` does not. The target reads a variable only when it comes from the command line, because `OWNER` is also a variable of `github-pipeline`. The items are the rows of `docs/requirements/` and the ADRs of `docs/adr/`. An ADR is read by id, by word, and by status, prints its title, status, file, and body, and has no owner, so `OWNER` lists rows only. The target does not rank, does not read the roadmap or the proposals, and does not follow links. This applies to both. `record` owns the target. |
