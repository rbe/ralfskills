# Requirements of record

The rows that the skill `r-record` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-4"></a>R-4 | Skill name matches directory | in force | The `name` in a skill's frontmatter matches its directory, and `make toon` fails when it does not. This applies to this collection and to every installed skill, and `r-record` owns the check. |
| <a id="r-65"></a>R-65 | Frontmatter is YAML | in force | APM reads the frontmatter of a `SKILL.md` as YAML. It refuses to install a collection when one skill does not parse, so each frontmatter value is one YAML string. `make toon` fails when a value breaks this. This applies to this collection and to a product skill, and `r-record` owns the check. |
| <a id="r-20"></a>R-20 | record writes ids and documents | in force | `r-record` is the only writer of ids and board documents, and a stage calls it by name before any id or document. A write that skips `r-record` fails that step. A skill that is not a stage adds one line to the section of the stage that runs, and it opens no history file. This applies to both, and `r-record` owns the write and states this rule once. |
| <a id="r-24"></a>R-24 | Product document homes | in force | A product repository keeps five homes, and `r-record` is the only writer. The roadmap holds the things to do and a proposal holds the plan of one row. An ADR or a requirement row holds a rule in force, and a history file reports one slice. The code and the tests are the current state, and a history file holds nothing that waits for a decision or for work. This applies to a product repository, and `r-record` owns the files. |
| <a id="r-67"></a>R-67 | Board templates | in force | `r-record` has one template for each board document in `templates/` and copies it at the first write. The scripts of `r-record` and `r-project-report` then read one layout. The next number of a kind comes from `make id KIND=<kind>`, as [R-13](#r-13) says. A list in the frontmatter is on one line and holds ids only. This applies to a product repository, and `r-record` owns the templates. |
| <a id="r-53"></a>R-53 | Where a choice that must hold goes | in force | When the owner answers a choice that must hold, `r-plan` asks `r-record` where it goes. `r-record` decides in this order: a small requirement row, a sentence in an ADR that fits, a new ADR. If no home fits, the agent asks the user, and a choice that need not hold has no home. This applies to both. `r-plan` owns the request, and `r-record` owns the write and the place. |
| <a id="r-55"></a>R-55 | An ADR may replace a skill rule | in force | An accepted ADR replaces a skill rule only when it is a divergence, and a divergence names the rule, what differs, and why. An ADR that names none of these is a finding in `r-review`. What `r-github-pipeline` says is not a divergence stays not allowed. This applies to a product repository. `r-record` owns the rule, and `r-review` owns the check. |
| <a id="r-56"></a>R-56 | ADR status and replacement | in force | `r-record` owns the ADR status, which is `Accepted` or `Superseded`. A new ADR names the ADR it replaces in `supersedes`, and `r-record` sets the replaced one to `Superseded`. The stages follow only an accepted ADR. This applies to a product repository, and `r-record` owns the status. |
| <a id="r-61"></a>R-61 | ADR body | in force | An ADR body has the sections `## Rule` and `## Why`, and `## Divergence` when it replaces a skill rule. Rule is what an agent must do, in sentences `r-review` can check, and Why is the reason and the options not chosen. This applies to a product repository, and `r-record` owns the sections. |
| <a id="r-26"></a>R-26 | Four history sections | in force | Every history file has the headings Plan, Develop, Review, and Release, and `r-record` rejects a file that misses one. A history file reports what was done, found, and not run, each as a fact. It is complete at every stage end. An item that waits goes to a roadmap row or a planned requirement row. A declined idea is a fact of the history file of its slice. This applies to a product repository. `r-record` owns the headings, and each stage owns its section. |
| <a id="r-58"></a>R-58 | Closing a task | in force | `r-release` writes the Release section and then asks `r-record` to close the task, whether the slice shipped or not. `r-record` stops when Plan, Develop, or Review still reads `Not invoked yet.` Otherwise it sets the status `closed` and deletes the roadmap rows that `roadmap:` names. An ADR and a requirement row stay in force. This applies to both, and `r-record` owns the steps. |
| <a id="r-27"></a>R-27 | Links are id keys | in force | An ADR, a proposal, and a history file name other documents by id in YAML keys. A list key holds ids only, as [R-13](#r-13) says. A test does not put an id in a path, and `r-review` fails an id in a path. This collection's rules are rows of `docs/requirements/` and use no YAML block, as [R-28](#r-28) says. This applies to a product repository, and `r-record` owns the keys. |
| <a id="r-69"></a>R-69 | Ids are links | in force | In running text under `docs/`, each id is a link to its item, so a person goes from one item to another with one click. An agent writes the plain id, `make links` writes the link, and `make links-check` fails on a wrong or missing link. This applies to both, and `r-record` owns the two targets. |
| <a id="r-13"></a>R-13 | Ids are never reused | in force | `r-record` issues every id from a counter in `docs/ids.yaml` that only grows. A number is never issued twice, also after its row or file is deleted. No list of retired ids exists. A history id has no counter and must be unique among the files. `make ids` fails on a duplicate id or an id above its counter, and the caller invents no id in prose. This applies to both, and `r-record` owns issuance. |
| <a id="r-110"></a>R-110 | Stages column of the skill index | in force | A skill that a stage loads has `stages` in its frontmatter, and `make toon` writes it as the last column of `docs/skill-index.toon`. A stage reads the rows whose `stages` names it, so a stage skill names no subskill or language skill to load. This applies to both. `r-record` owns the column, and each stage skill owns the call. |
| <a id="r-113"></a>R-113 | Defect report form | in force | `r-record` has `references/defect-report.md`, the form of a defect report in eight parts. A defect that waits is a roadmap row of the kind `defect`, and its proposal holds the report. A finding fixed in the change has the first five parts as sentences in the Review section. This applies to both, and `r-record` owns the form, and `r-review` points to it. |
| <a id="r-6"></a>R-6 | Generated TOON indexes | in force | `make toon` writes the ADR index and the skill index, and hand-editing a generated index is a defect. An agent runs the target before it reads an index. When the repository keeps `docs/requirements/` and has no ADR file, the target writes `docs/requirements-index.toon` instead of the ADR index. This applies to both, with that switch, and `r-record` owns the target. |
| <a id="r-28"></a>R-28 | This collection's board | in force | This collection is not a product repository: it has no `docs/ROADMAP.md` and no `docs/adr/`. Each rule is one row in `docs/requirements/<skill>.md`, in the file of the skill that owns it. A row states the intent and the reason of a rule. The skill text holds the details, and no row repeats them. A planned row is open work or an open question that names its choices. A closed task turns its row to in force or deletes it. This applies to this collection, and `r-record` owns the distinction. |
| <a id="r-1"></a>R-1 | Tests name a requirement | in force | A test names the requirement it proves with `id:` in its header or metadata, and a test with no id fails `r-develop` and `r-review`. On a product repository the id is an ADR id or the id of a requirement row in force. A roadmap row and a planned row are not rules, so a test names neither. This applies to both. `r-develop` and `r-review` own the stop, and `r-record` owns the matching line. |
| <a id="r-84"></a>R-84 | make req reads one row | in force | `make req` prints the requirement rows and the ADRs that a question needs, so an agent reads one row and not a whole file. It filters by `ID`, `Q`, `OWNER`, and `STATUS`. It does not rank, does not read the roadmap or the proposals, and does not follow links. This applies to both, and `r-record` owns the target. |
| <a id="r-106"></a>R-106 | Close compacts the board | in force | When `r-record` closes a task, it deletes the proposal that the task started from, because Git keeps its text. It shortens the history file of the task to at most 150 words below the frontmatter and rewrites no other history file. The cleanup of the whole board stays with `r-board-merge-report` and `r-board-merge`. This applies to both, and `r-record` owns the steps. |
| <a id="r-130"></a>R-130 | Board check in make test | in force | `make board-check` runs `make ids`, `make links-check`, and `make test-ids`, and `make test` runs it first. So the gates and CI fail on a repeated id, an id that is no link, and a test with no id, as [R-1](#r-1), [R-13](#r-13), and [R-69](#r-69) say. `r-record` owns the target, and `r-project-report` adds `test-ids`. This applies to both. |
| <a id="r-153"></a>R-153 | Glossary of terms | in force | `docs/glossary.md` holds one row for each term that the user and the agents use: the term, its meaning in one sentence, and its path. The communication contract tells each agent to use these terms and to add a missing term first. `r-system-state-report` reads and extends the file and builds no own table. The reason is that a term then means the same thing in each chat. This applies to both. `r-record` owns the file, and the communication contract owns the rule of use. |
