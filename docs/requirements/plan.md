# Requirements of plan

The rows that the skill `r-plan` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-49"></a>R-49 | Plan closes a slice | in force | `r-plan` grills a change before editing, one question at a time, until the slice is one sentence with an out-of-scope line. It asks no question that an accepted ADR, a requirement row in force, or an open proposal already answers. A request that [R-59](develop.md#r-59) sends to `r-develop` is not a `r-plan` request. This applies to a product repository, and to this collection when someone plans a change here. `r-plan` owns the grill. |
| <a id="r-7"></a>R-7 | Boundary and pattern | in force | Before the slice closes, `r-plan` names who owns state, what may call what, and the pattern. `r-review` fails the change when code ignores that pattern, and it names no other one. This applies to both. `r-plan` owns the sentence, and `r-review` owns the check. |
| <a id="r-14"></a>R-14 | Costly choices wait | in force | `r-plan` step 5 follows the boundary step and holds only this rule: prefer the smallest design that stays operable and maintainable. When a choice is expensive to reverse, name the options, recommend one, and wait. This applies to both, and `r-plan` owns the step. |
| <a id="r-22"></a>R-22 | When setup and pipeline run | in force | `r-plan` invokes `r-project-setup` only when the Makefile is missing or the slice adds or overrides a target. `r-release` invokes `r-github-pipeline` when the change touches delivery, and `r-project-setup` only when that same change adds or overrides a Make target. [R-57](release.md#r-57) says how a slice ships. This applies to a product repository, and `r-plan` and `r-release` own the invocations. |
| <a id="r-25"></a>R-25 | One home for the grill | in force | A grill has one home, so copies of it cannot drift. Work to implement now goes in the Plan section of a history file. Work for later goes in a proposal with its roadmap row. When a proposal is picked up, `r-record` creates the history file, which cites the proposal id. This applies to a product repository, and `r-plan` and `r-record` own the choice of home. |
| <a id="r-30"></a>R-30 | Optional subskills | in force | The subskills are `r-security`, `r-privacy`, `r-ux-ui-design`, `r-api-design`, `r-observability`, and `r-performance`. Each is optional, and the installed set is the set that runs. `r-plan` asks each installed one before the slice closes, and `r-review` checks each one after the change, in the order of the skill index. This applies to both. `r-plan` and `r-review` own the call, and each subskill owns its questions. |
| <a id="r-50"></a>R-50 | When to use an outside project | in force | Use an outside project only when it costs more than the rest of the skill set to build. It must be maintained, versioned, and specified or tested, and followed rather than vendored. It must leave the four stages as the lifecycle, have a fitting license, and have no telemetry. Use APM and the `SKILL.md` layout. Do not vendor a prompt bundle or an ADR toolkit. This applies to this collection and to a product repository that adopts a tool. `r-plan` owns the choice when it is expensive to reverse, as [R-14](#r-14) says. |
