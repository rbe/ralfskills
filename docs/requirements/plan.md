# Requirements of plan

The rows that the skill `plan` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-49"></a>R-49 | Plan closes a slice | in force | `plan` grills a change before editing. Use it when a request is new, vague, or would change a rule, an ADR, the roadmap, or a proposal. A request that [R-59](develop.md#r-59) sends to `develop` is not a `plan` request. Work runs in this order. Run `make toon` and read the board for this repository. For each skill-index row whose `kind` is `check`, read the skill and ask its questions in the order of [R-30](#r-30). Ask one question, then wait. Before the slice closes, `plan` asks what the result looks like: the output or the interface, the empty case, and the error case. Stop when the slice is one sentence, with an out-of-scope line. Do not ask a question an accepted ADR, a requirement row in force, or an open proposal already answered. Then name the boundary and the pattern, then evaluate architecture with the words in [R-14](#r-14), then ask where a choice that must hold goes, as [R-53](record.md#r-53) says, then invoke `project-setup` only as [R-22](#r-22) says, then stop when the slice needs a language the skill index does not list. This applies to a product repository, and to this collection when someone plans a change here. `plan` owns the grill. |
| <a id="r-7"></a>R-7 | Boundary and pattern | in force | Before the slice closes, `plan` names who owns state, what may call what, and the pattern. When the boundary keeps the slice out of a package, `plan` names each existing function there that the slice needs, and says whether the slice moves it, exports it, or repeats it. That is step 4, after the one-question grill. Architectural patterns are part of that grill. Stop when that sentence is missing. `review` fails the change when code ignores the pattern `plan` named. `plan` chooses the pattern. `review` does not name a different one. Clean Code catalogues and pattern catalogues are not separate skills. This applies to both. `plan` owns the sentence. `review` owns the check. |
| <a id="r-14"></a>R-14 | Costly choices wait | in force | `plan` step 5 is this text, and only this text, immediately after the boundary step. The words are: Evaluate architecture, scalability, and code quality against the constraints of this system. Prefer the smallest design that stays operable and maintainable. When a choice is expensive to reverse, name the options, recommend one, and wait. Otherwise implement it in small modules. This applies to both. `plan` owns the step. |
| <a id="r-22"></a>R-22 | When setup and pipeline run | in force | `plan` invokes `project-setup` when the Makefile is missing, or when the slice adds or overrides a target. It does not invoke `project-setup` otherwise. `release` invokes `github-pipeline` when the change touches the workflow, the version, publish, the image, cleanup, or retention. `release` invokes `project-setup` only when that same delivery change adds or overrides a Make target. `release` does not call `project-setup` on every ship. When the task does not ship, [R-26](record.md#r-26) says what the Release section holds. [R-57](release.md#r-57) says how a slice ships. This applies to a product repository. `plan` and `release` own the invocations. |
| <a id="r-25"></a>R-25 | One home for the grill | in force | [R-24](record.md#r-24) names five homes. Three of them are a roadmap row, a proposal, and a history file. Do not copy a grill into all three. A slice that starts at `develop` gets its history file as [R-59](develop.md#r-59) says. Implement now: `plan` asks `record` for a history id, writes the questions and answers in Plan, including the boundary and the pattern, and sets Develop, Review, and Release to `Not invoked yet.` Do not copy the grill into the roadmap. Implement later: `plan` asks `record` for a proposal id and writes `docs/proposals/<id>.md`, and asks `record` for the roadmap row that names it. Do not create a history file. When a proposal is picked up, `record` creates the history file, sets `proposals:` to that id, sets the proposal status to `started`, and sets `roadmap:` to the roadmap row of the proposal. The Plan section cites the proposal id. Develop does not copy the proposal. This applies to a product repository. `plan` and `record` own the choice of home. |
| <a id="r-30"></a>R-30 | Optional subskills | in force | The subskills are `security`, `privacy`, `ux-ui-design`, and `api-design`. Each is optional. The installed set is the set that runs. `plan` asks each installed one before the slice closes. `review` checks each installed one after the change. Both follow `order` on the skill index: `security` 10, `privacy` 20, `ux-ui-design` 30, `api-design` 40. The lines of the checks follow the general rules. If no `check` row exists, write `checks: none installed`. A row without a line fails the step. A check that does not apply to the change is one line that says why. The line for a skill that is not installed is `<name>: not installed`, and that line is used only when it is not installed. This applies to both. `plan` and `review` own the call. Each subskill owns its questions. |
| <a id="r-50"></a>R-50 | When to use an outside project | in force | An outside project is used only when it costs more than the rest of the skill set to build, is maintained, versioned, and specified or tested, is depended on or followed rather than vendored, leaves the four stages as the lifecycle, has a fitting license, and has no telemetry. Use APM and the `SKILL.md` layout. Do not vendor a prompt bundle or an ADR toolkit. The ADR index is the Make target in `record`. This applies to this collection and to a product repository that adopts a tool. `plan` owns the choice when the choice is expensive to reverse, as [R-14](#r-14) says. |
