# Requirements of collection

Each row is a rule that holds or work to do. The status `in force` is a rule that this skill set fulfills. The status `planned` is open work, or an open question whose statement names the choices. The rows in force are enough to reimplement the skill set. A sentence that begins with `This applies to` says where the row holds: this collection, a product repository, or both. The rows stand in one file for each skill that owns them, in `docs/requirements/<skill>.md`. A row with no owning skill stands in this file. The index `docs/requirements-index.toon` lists the id, the title, the status, the file, and the owner of each row.

| <a id="r-16"></a>R-16 | APM skill package | in force | ralfskills is an APM skill collection. Each skill is one directory `skills/r-<name>/SKILL.md`. There is no root `SKILL.md`. Install the set with the one `podman run` line of the README, which runs `apm install` in an image, or install selected skills by name with `make apm ARGS='...'`. The `apm.yml` of a project needs `name` and `version`. A project commits `.claude/skills/`, `apm.yml`, and `apm.lock.yaml`, because its Makefile includes files from `.claude/skills/`. The skills in the set are the ones that [R-60](project-setup.md#r-60) lists, one skill for each directory of `skills/`. This applies to this collection. APM is the installer. |
| <a id="r-17"></a>R-17 | Install path and agent-agnostic text | in force | Installed skills live under `.claude/skills/`, the APM target `claude`. Only the Agents section of the `CLAUDE.md` template names models. Command-line tools such as `grep` or `podman` are not AI coding tools. A unit test scans each `SKILL.md` and each reference file for these names. This applies to this collection and to the skills a product repository installs. |

This applies to this collection and to a product repository that uses the skills. [R-29](migrate-docs.md#r-29) says how an old `AGENTS.md` goes. | <a id="r-19"></a>R-19 | Four numbered stages | in force | The stage skills are `r-plan`, `r-develop`, `r-review`, and `r-release`, in that order. Each has one `<steps>` block, a short numbered list of its work in order. A duty of a stage is a numbered step, not only a paragraph. Each stage has a step that asks `r-record` to write its history section. That step is not always the last step. The frame that every skill repeated before is in the general rules, as [R-76](project-setup.md#r-76) says: the stop on the old board, `r-record` before an id or a document, and no later step after a stop. `r-record` has the modes write and close. Write mode starts with the id check. Close mode starts with the check that Plan, Develop, and Review were written. This applies to both. Each named skill owns its own list. |

This applies to a product repository. The README owns the text. |

| <a id="r-66"></a>R-66 | Makefile templates of the language skills | in force | `r-python` has `templates/Makefile.python`, `templates/coveragerc`, and `python.mk`. `r-node` has `templates/Makefile.node`, `templates/prettierignore`, `templates/eslint.config.mjs`, and `node.mk`. `r-go` has `templates/Makefile.golang` and `go.mk`. `r-jvm` has `templates/Makefile.gradle`, `templates/build.gradle`, `templates/settings.gradle`, `templates/checkstyle.xml`, and `jvm.mk`. The language targets are in the include files, not in the templates, as [R-122](#r-122) says. The project sets its name in `settings.gradle`, and its group and version in `build.gradle`. In the JVM template, `$(GRADLE)` runs the Gradle wrapper in Podman. In `jvm.mk`, `make wrapper` writes the wrapper alone, and `make jvm-tooling` writes the build files first and the wrapper after them, because Gradle needs the settings file to write the wrapper. `make jvm-tooling` counts `build.gradle.kts` and `settings.gradle.kts` as present, so a project with a Kotlin build file gets no second build file. A test reads the recipe in `skills/r-jvm/jvm.mk`. Each Makefile template fills every command variable of the Make contract for a project on `project.mk`: setup, build, test, integration, format, format-fix, lint, coverage, and the changed tests. In `node.mk`, `$(NODE)` runs Node and npm in Podman, and `make npm ARGS=...` runs one npm command, such as adding a dependency. `make node-tooling` creates `package.json` with its name, version, and module type when it is missing, adds `NODE_DEV_TOOLS` as exact dev dependencies, writes `.prettierignore`, `eslint.config.mjs`, and `.editorconfig` when they are missing, adds `node_modules/` and `coverage/` to `.gitignore`, and runs `make format-fix`. A Node library sets `exports` and `files`, so `make build` packs the source and nothing else. Each language skill has one tooling target, in its include file, for a new project or a project with no tooling: `make node-tooling`, `make python-tooling`, `make jvm-tooling`, and `make go-tooling`. `node-tooling`, `jvm-tooling`, and `go-tooling` create the manifest when it is missing, and `python-tooling` creates none. Each one writes the config files and `.editorconfig` that are missing, adds its lines to `.gitignore`, and runs `make format-fix`. `go-tooling` runs it only when the project has a Go package. A file or a dependency already in the project stays. A second run changes nothing. In the Python template, `UNIT_TESTS` is every file `tests/test_*.py` and `tests/*/test_*.py`, so a new test file runs with no change to the Makefile, and Ruff does not read `.claude/`, `apm_modules/`, or `docs/`. For a project with no Makefile, `r-project-setup` asks which language skill the project uses and copies its templates. An existing Makefile gets only the lines it lacks. `r-project-setup` runs the tooling target when the Makefile came from a template in that run, or when a file that the target writes is missing. This applies to a product repository. Each language skill owns its templates and its include file. |
| <a id="r-122"></a>R-122 | Include files of the language skills | in force | Each language skill has one include file with the Make targets of its language. `r-node` has `node.mk` with `npm` and `node-tooling`. `r-python` has `python.mk` with `python-tooling`. `r-go` has `go.mk` with `go` and `go-tooling`. `r-jvm` has `jvm.mk` with `wrapper`, `jvm-tooling`, and `podman-socket`. A project includes the file from the installed skill after `project.mk` or `sdlc.mk`, for example `include .claude/skills/r-node/node.mk`, and keeps no copy of these targets in its Makefile, so the copies cannot drift. Each Makefile template of the language skills includes its file and defines none of those targets. The Node and Gradle templates of `r-github-pipeline` include `node.mk` and `jvm.mk` too, so a pipeline project has `make npm` and `make podman-socket`. The templates keep the command variables, `$(GRADLE)`, `$(GRADLE_PODMAN)`, and the `run` target of the Go template, because the project owns them. Each file has a guard, the marker `# help-group: Tools` from [R-11](project-setup.md#r-11), `.PHONY`, and `.DEFAULT_GOAL := help` at its end. Each variable that a recipe needs has a recursive `?=` default, so a project that sets the variable before the include keeps its value. These are `NODE`, `NODE_IMAGE`, `NODE_VERSION`, and `NODE_DEV_TOOLS` in `node.mk`, `GO_IMAGE`, `GO_CACHE`, `GO_OPTS`, `GO_RUN`, `GO`, and `MODULE` in `go.mk`, and `JDK_IMAGE`, `GRADLE_VERSION`, `GRADLE_IMAGE`, `GRADLE_RUN`, and `PODMAN_SOCKET` in `jvm.mk`. `podman-socket` does nothing when Podman runs through a machine, which `ServiceIsRemote` says. Otherwise it starts the socket with `systemctl --user start podman.socket` or with `podman system service`, checks with `podman unshare test -S` that rootless Podman sees the socket, and runs `podman system migrate` once when it does not. The root `Makefile` of this collection is Python only and includes no language file. This applies to a product repository. Each language skill owns its file. |
| <a id="r-51"></a>R-51 | Communication contract | in force | The communication contract lives in `CLAUDE.md`, because every agent reads that file in every session. It is written for a reader who reads each reply once, often after a break, and decides from it. The contract has five parts. Names: use the user's words and the project's identifiers, one name for one thing, define a label you invented and an abbreviation at first use. Sentences: the first sentence states the understood intent, and stops when it is wrong; one statement per sentence, at most 25 words, active voice with a named actor, the condition before the result, full sentences. Content: the specific noun, number, path, or name; a measure when something is better; how you know each statement about the system (ran, read, or assumed); literal language. Questions: before a question, the agent gives the context (what the item is, what holds now, the choices, and the effect of each choice) and recommends one choice. It writes each id with its title and as a Markdown link to its definition, never a bare id, so the user answers without opening a file. Scope: the rules apply to what the agent writes to the user, not to code, quotes, or a text for another reader. English follows ASD-STE100. German follows "Deutsch für die Technische Kommunikation" (tekom Deutschland e.V.). Name the standards. Do not copy their text. Keep German and English separate. Each rule is one line, and the contract has one Not and But example. This applies to this collection and to a product repository. A product repository gets the contract from the entry-file template, as [R-60](project-setup.md#r-60) says. No `SKILL.md` restates the contract. |
| <a id="r-105"></a>R-105 | Skill names start with r- | in force | Each skill of the collection has a folder name and a `name` that start with `r-`. The `name` equals the folder name. The prefix lets a project install skills of other collections without a name clash. A project calls `/r-plan`, and its `apm.yml`, its `CLAUDE.md`, and its Makefile include `.claude/skills/r-<name>/...` use the prefixed name. A Make target keeps its name. A file in `docs/requirements/` keeps the bare name of its owner skill. A unit test checks the prefix and the equal name of every skill. This applies to this collection. |

| <a id="r-124"></a>R-124 | Guard hooks | in force | The collection ships two hooks that run before each Bash command of the agent. `hooks/r-guards.json` names them, and the scripts are in `hooks/scripts/`. `block-bare-git-add.sh` refuses a command that stages the whole working copy: `git add -A`, `git add .`, `git add --all`, `git add -u`, or `git add :/` without a pathspec, and `git commit -a` or `--all`. This is the rule of [R-114](release.md#r-114). `block-python-file-write.sh` refuses an inline Python command (`python`, `python3`, `uv run python`, or `make py`) that has a write call and a quoted relative path outside `build/`. A Python command that only reads passes. Each refusal names the command to use instead. The scripts need only POSIX `sh`, `awk`, `grep`, and `sed`, and no `jq`. If the hook input has no command, the script exits 2, so Claude Code blocks the command and shows the message. `apm install` merges the hooks into `.claude/settings.json` of a project and copies the scripts. `.claude/settings.json` of this collection runs the same scripts from `hooks/scripts/`. A unit test runs each script with sample hook input. This applies to this collection and to a product repository. |
