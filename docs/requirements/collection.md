# Requirements of collection

Each row is a rule that holds or work to do. The status `in force` is a rule that this skill set fulfills. The status `planned` is open work, or an open question whose statement names the choices. The rows in force are enough to reimplement the skill set. A sentence that begins with `This applies to` says where the row holds: this collection, a product repository, or both. The rows stand in one file for each skill that owns them, in `docs/requirements/<skill>.md`. A row with no owning skill stands in this file. The index `docs/requirements-index.toon` lists the id, the title, the status, the file, and the owner of each row.

| <a id="r-16"></a>R-16 | APM skill package | in force | ralfskills is an APM skill collection. Each skill is one directory `skills/<name>/SKILL.md`. There is no root `SKILL.md`. Install the set with the one `podman run` line of the README, which runs `apm install` in an image, or install selected skills by name with `make apm ARGS='...'`. The `apm.yml` of a project needs `name` and `version`. A project commits `.claude/skills/`, `apm.yml`, and `apm.lock.yaml`, because its Makefile includes files from `.claude/skills/`. The skills in the set are `plan`, `develop`, `review`, `release`, `record`, `migrate-docs`, `project-setup`, `github-pipeline`, `project-report`, `security`, `privacy`, `ux-ui-design`, `api-design`, `node`, `python`, `shell`, `jvm`, `go`, `onboard`, `system-state-report`, `board-merge-report`, and `board-merge`. This applies to this collection. APM is the installer. |

| <a id="r-19"></a>R-19 | Four numbered stages | in force | The stage skills are `plan`, `develop`, `review`, and `release`, in that order. Each stage has a step that asks `record` to write its history section. That step is not always the last step. The frame that every skill repeated before is in the general rules, as [R-76](project-setup.md#r-76) says: the stop on the old board, `record` before an id or a document, and no later step after a stop. `record` has the modes write and close. Write mode starts with the id check. Close mode starts with the check that Plan, Develop, and Review were written. This applies to both. Each named skill owns its own list. |

| <a id="r-100"></a>R-100 | Test of the collection in a test repository | in force | The owner tests the collection in a test repository before a version tag of the collection, with a branch of the collection that is not tagged yet. Three limits hold: never push to or change the default branch of the test repository, never delete a release, a tag, or a package version for real (a cleanup target runs only with `DRY_RUN=1`), and work only on the two test branches. The pull request targets get the base branch through `DEFAULT_BRANCH`. The README section "Test the collection in a test repository" holds the steps: create the branches, install the branch, run the gates and the pipeline, use the branches again, and remove them. [R-72](#r-72) states the path to a tagged version. This applies to this collection. The README owns the text. |

| <a id="r-66"></a>R-66 | Makefile templates of the language skills | in force | `python` has `templates/Makefile.python` and `templates/coveragerc`. `node` has `templates/Makefile.node`, `templates/prettierignore`, and `templates/eslint.config.mjs`. `go` has `templates/Makefile.golang`. `jvm` has `templates/Makefile.gradle`, `templates/build.gradle`, `templates/settings.gradle`, and `templates/checkstyle.xml`. The project sets its name in `settings.gradle`, and its group and version in `build.gradle`. In the JVM template, `$(GRADLE)` runs the Gradle wrapper in Podman, and `make wrapper` writes the wrapper alone, and `make jvm-tooling` writes the build files first and the wrapper after them, because Gradle needs the settings file to write the wrapper. `make jvm-tooling` counts `build.gradle.kts` and `settings.gradle.kts` as present, so a project with a Kotlin build file gets no second build file. A test reads the recipe in `skills/jvm/templates/Makefile.gradle`. Each Makefile template fills every command variable of the Make contract for a project on `project.mk`: setup, build, test, integration, format, format-fix, lint, coverage, and the changed tests. In the Node template, `$(NODE)` runs Node and npm in Podman, and `make npm ARGS=...` runs one npm command, such as adding a dependency. `make node-tooling` creates `package.json` with its name, version, and module type when it is missing, adds `NODE_DEV_TOOLS` as exact dev dependencies, writes `.prettierignore`, `eslint.config.mjs`, and `.editorconfig` when they are missing, adds `node_modules/` and `coverage/` to `.gitignore`, and runs `make format-fix`. A Node library sets `exports` and `files`, so `make build` packs the source and nothing else. Each language template has one tooling target for a new project or a project with no tooling: `make node-tooling`, `make python-tooling`, `make jvm-tooling`, and `make go-tooling`. `node-tooling`, `jvm-tooling`, and `go-tooling` create the manifest when it is missing, and `python-tooling` creates none. Each one writes the config files and `.editorconfig` that are missing, adds its lines to `.gitignore`, and runs `make format-fix`. `go-tooling` runs it only when the project has a Go package. A file or a dependency already in the project stays. A second run changes nothing. In the Python template, `UNIT_TESTS` is every file `tests/test_*.py` and `tests/*/test_*.py`, so a new test file runs with no change to the Makefile, and Ruff does not read `.claude/`, `apm_modules/`, or `docs/`. For a project with no Makefile, `project-setup` asks which language skill the project uses and copies its templates. An existing Makefile gets only the lines it lacks. `project-setup` runs the tooling target when the Makefile came from a template in that run, or when a file that the target writes is missing. This applies to a product repository. Each language skill owns its templates. |
| <a id="r-51"></a>R-51 | Communication contract | in force | The communication contract lives in `CLAUDE.md`, because every agent reads that file in every session. It is written for a reader who reads each reply once, often after a break, and decides from it. The contract has five parts. Names: use the user's words and the project's identifiers, one name for one thing, define a label you invented and an abbreviation at first use. Sentences: the first sentence states the understood intent, and stops when it is wrong; one statement per sentence, at most 25 words, active voice with a named actor, the condition before the result, full sentences. Content: the specific noun, number, path, or name; a measure when something is better; how you know each statement about the system (ran, read, or assumed); literal language. Questions: before a question, the agent gives the context (what the item is, what holds now, the choices, and the effect of each choice) and recommends one choice. It writes each id with its title and as a Markdown link to its definition, never a bare id, so the user answers without opening a file. Scope: the rules apply to what the agent writes to the user, not to code, quotes, or a text for another reader. English follows ASD-STE100. German follows "Deutsch für die Technische Kommunikation" (tekom Deutschland e.V.). Name the standards. Do not copy their text. Keep German and English separate. Each rule is one line, and the contract has one Not and But example. This applies to this collection and to a product repository. A product repository gets the contract from the entry-file template, as [R-60](project-setup.md#r-60) says. No `SKILL.md` restates the contract. |
