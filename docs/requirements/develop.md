# Requirements of develop

The rows that the skill `r-develop` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-59"></a>R-59 | A slice that starts at develop | in force | A request that names a source file, a failing test, or a defect row of the roadmap starts at `r-develop`. A fix is such a request. When no history file exists, `r-develop` creates the branch and asks `r-record` for the file, and the Plan section says why `r-plan` was not invoked. The slice then goes through `r-review` and `r-release` like any other. This applies to both. `r-develop` owns the request, and `r-record` owns the file. |
| <a id="r-54"></a>R-54 | Stages read the accepted ADRs | in force | `r-develop` reads the accepted ADRs that name a skill of the slice before it edits, and it stops when the change would break one. `r-review` opens the same ADRs and writes a finding for a break. A repository that keeps `docs/requirements/` and no `docs/adr/` reads its requirement index and `make req` instead. This applies to a product repository, and `r-develop` and `r-review` own the read. |
| <a id="r-47"></a>R-47 | Method, name, and test hygiene | in force | A method does one thing or only composes other methods, and each unit takes its name from the domain. A behaviour change has a unit test, and a test has no skip, no silent catch, and no secret or personal data in a fixture. `r-develop` stops when one of these fails, and `r-review` writes a finding for it. This applies to both. `r-develop` owns the stops, `r-review` owns the one check, and `r-plan` still chooses the pattern, as [R-7](plan.md#r-7) says. |
| <a id="r-8"></a>R-8 | Fast feedback in develop | in force | `r-develop` runs `make coverage` and `make test-changed`, not the gates, and it stops when either fails or runs outside Make. `r-review` runs all six gates once, as [R-127](project-setup.md#r-127) says. The reason is one run of the gates on the final content, not a run after each edit. This applies to both. `r-develop` owns the fast feedback, and `r-review` does not weaken a test. |
| <a id="r-34"></a>R-34 | Installed languages are the stack | in force | The installed skill list is the stack. `r-develop` stops before it introduces a language that is not installed. It reads `docs/skill-index.toon` to find the language skill that matches the files in hand. Two languages mean two disjoint file sets, and one set is finished before the other. This applies to both. `r-develop` owns the dispatch, and each language skill owns its files. |
| <a id="r-144"></a>R-144 | Regression test fails first | in force | A regression test fails on the code before the fix, and `r-develop` runs it once against the old code to prove this. The reason is that a test that passes on the old code proves nothing about the fix. This applies to a product repository that installs `r-develop`, and `r-develop` owns this rule. |
| <a id="r-145"></a>R-145 | No mock of the step under test | in force | A test does not mock the step whose failure it tests. It stubs the edge of the system and runs the step. The reason is that a mock of that step lets the fault through while the suite stays green. This applies to a product repository that installs `r-develop`, and `r-develop` owns this rule. |
| <a id="r-146"></a>R-146 | Temporary block in a document | in force | If code and a document must differ for a short time because of the merge order, the document gets a block `Temporary (until #NNN)`. The block names the gap, the reason, and the condition that removes it. The change that closes the gap removes the block. The reason is that the reader then knows the difference has an end. This applies to a product repository that installs `r-develop`, and `r-develop` owns this rule. |
