# Requirements of r-api-design

The rows that the skill `r-api-design` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-10"></a>R-10 | API shape questions | in force | `r-api-design` makes `r-plan` ask what a route or an export is, and makes `r-review` check that the change matches the answers. The reason is that the contract and the handler change together, and a caller relies only on what the answers named. The route catalogue stays in the product, as [R-52](collection.md#r-52) says. This applies to both, when the skill is installed, and `r-api-design` owns the questions. |
| <a id="r-131"></a>R-131 | Error status is kept | in force | `r-api-design` makes `r-review` check that a thrown error that carries a status keeps it. A body over the size limit answers 413, not 500. The reason is that a client cannot act on a generic server error. This applies to a product repository that installs `r-api-design`, and `r-api-design` owns this rule. |
| <a id="r-132"></a>R-132 | 5xx body is generic | in force | `r-api-design` makes `r-review` check that a 5xx body has a fixed generic message and that the detail goes to the log once. The reason is that an internal message can quote a path or a part of the request. This applies to a product repository that installs `r-api-design`, and `r-api-design` owns this rule. |
| <a id="r-133"></a>R-133 | Missing record answers 404 | in force | `r-api-design` makes `r-plan` ask what a mutation of a missing record answers. It makes `r-review` check that the answer is 404, not success. The reason is that a success for a change that did not happen hides the fault. This applies to a product repository that installs `r-api-design`, and `r-api-design` owns this rule. |
| <a id="r-134"></a>R-134 | Record verbs and statuses | in force | `r-api-design` makes `r-review` check the statuses of the record verbs. POST answers 201 with the record. PATCH answers 200 with the record. DELETE of one record answers 204 with no body. The reason is that the client needs no second request. This applies to a product repository that installs `r-api-design`, and `r-api-design` owns this rule. |
| <a id="r-135"></a>R-135 | One error handler, no HTML on the API | in force | `r-api-design` makes `r-plan` ask which one error handler turns an error into a response. It makes `r-review` check that a path of the API never answers HTML, an unknown path included. The reason is that a client of the API parses the error body as data. This applies to a product repository that installs `r-api-design`, and `r-api-design` owns this rule. |
