# Requirements of r-project-setup

The rows that the skill `r-project-setup` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-60"></a>R-60 | Entry file template | in force | `r-project-setup` has the template `templates/CLAUDE.md`, the one source of the entry file for a product repository. Setup mode writes the file from the template when it is missing. Otherwise it adds each missing paragraph and the import line of `rules.md`. It deletes each copy of a rule that `rules.md` states and names each deleted sentence in the reply. The skills of the collection are the stages `r-plan`, `r-develop`, `r-review`, and `r-release`; the other skills `r-record`, `r-project-report`, `r-project-setup`, `r-github-pipeline`, `r-migrate-docs`, `r-onboard`, `r-system-state-report`, `r-board-merge-report`, `r-board-merge`, `r-skills-review`, and `r-component-upgrade`; the language skills `r-node`, `r-python`, `r-shell`, `r-jvm`, and `r-go`; and the subskills `r-security`, `r-privacy`, `r-ux-ui-design`, `r-api-design`, `r-observability`, and `r-performance`. This list is the one list of the skills, and each other row points here. This applies to a product repository, and `r-project-setup` owns the template. |
| <a id="r-109"></a>R-109 | Agents section | in force | `CLAUDE.md` and `templates/CLAUDE.md` have the section `## Agents`. It assigns work by model strength and has each brief name the files and the acceptance check. The reviewing model re-checks each claim of an agent. A skill file names no model. This applies to this collection and to a product repository, and `r-project-setup` owns the template. |
| <a id="r-111"></a>R-111 | Drift check of the skill text | in force | `check-docs` fails when a `SKILL.md` or a reference file of an installed skill names a skill path or a `make <target>` that does not exist. In a product repository, a target that only a skill that is not installed defines is not missing. The `test` target runs it first, so CI runs it with the test job. This applies to both, and `r-project-setup` owns the target. |
| <a id="r-112"></a>R-112 | Stage addenda | in force | A project may add a project skill `<project>-<stage>`, and the stage reads it after its own steps. The sentence that says so stands once in `CLAUDE.md` and in the template, and no stage skill repeats it. This applies to this collection and to a product repository, and `r-project-setup` owns the template. |
| <a id="r-76"></a>R-76 | General rules, tag shape, and reference files | in force | The rules that hold for every skill stand once, in `rules.md` of `r-project-setup`, which `CLAUDE.md` and the template import with one line. A change to a rule is then one edit in this collection and none in a product repository. A `SKILL.md` holds what an agent needs on every run. A table, a sample, or a conditional rule goes to a file in `references/`. That file is one level deep. The body of a `SKILL.md` is XML tags with no Markdown heading. The frontmatter description says what the skill does and then when to use it, in the third person. This applies to this collection. Each skill owns its files, and `r-project-setup` owns the template. |
| <a id="r-21"></a>R-21 | Old board stops other skills | in force | The general rules run `make old-board` before the first skill, and if it fails, the only skill is `r-migrate-docs`. No `SKILL.md` other than that of `r-migrate-docs` names a path of the old board, and a unit test checks this. This applies to both, and `r-migrate-docs` is the skill that may continue. |
| <a id="r-71"></a>R-71 | Shared contract targets | in force | `contract.mk` of `r-project-setup` has the targets of the Make contract. Both `project.mk` and `sdlc.mk` include it, so a project that switches between them keeps the same targets. A template sets command variables and defines no contract target again, and a test fails when one does. `container.mk` has the image targets for every project that includes `sdlc.mk`. This applies to a product repository. `r-project-setup` owns `contract.mk`, and `r-github-pipeline` owns the rest. |
| <a id="r-73"></a>R-73 | Doctor and src layout | in force | `make doctor` checks the host and fails with the fix, and it is the first prerequisite of `setup`. A Python project with a `src/` layout runs its tests with no install step. This applies to a product repository. `r-project-setup` owns `doctor.mk` and `podman-python.mk`, and `r-project-report` owns `cover_tests.py`. |
| <a id="r-9"></a>R-9 | Existing formatter and linter | in force | The formatter and the linter are existing tools that the language skill names. Do not write a formatter or a linter, and do not add a second one for one language. `make format` changes no file, and `make format-fix` rewrites files with the same formatter. This applies to both. The language skill owns the tool name, and `r-project-setup` owns the targets. |
| <a id="r-12"></a>R-12 | Diff coverage | in force | `make coverage` writes a diff coverage report for the lines this change touched, and it applies no repository-wide percentage. `r-develop` stops when the report is missing, and `r-review` reads it. A repository-wide percentage used as the result is a finding. This applies to both. `r-project-setup` owns the target, and `r-develop` and `r-review` run it. |
| <a id="r-40"></a>R-40 | Podman is the engine | in force | `make build`, `make test`, and `make run` call Podman, on a laptop and in CI. No divergence allows a toolchain command on the host, as [R-75](#r-75) says. Host mode of [R-129](#r-129) is the one exception. This applies to both. `r-project-setup` owns the rule, and `r-github-pipeline` follows it and names Docker as not allowed. |
| <a id="r-41"></a>R-41 | XDG local paths | in force | Local config, data, state, and cache use the XDG directories on macOS and Linux. This applies to a product repository, and `r-project-setup` owns the rule. |
| <a id="r-43"></a>R-43 | Host Python is Make | in force | All Python on the host goes through Make in Podman, so a direct host `python3`, `python`, `pip`, or `.py` file is a failed step. `$(PYTHON)` runs the image, and a one-off command is `make py ARGS='...'`. This applies to both, and `r-project-setup` owns `podman-python.mk`. |
| <a id="r-11"></a>R-11 | Help is the default goal | in force | `help` is the default goal of every makefile, so `make` with no arguments prints the same help as `make help`. A project sets no other default goal. `help.mk` lists every target with a `##` comment in fixed groups, so every project shows the same groups in the same order. This applies to both. `r-project-setup` owns the goal, and `r-github-pipeline` defines `help` as well, so one include is enough. |
| <a id="r-44"></a>R-44 | Make 3.81 and POSIX sh | in force | Recipes run on GNU Make 3.81 or newer, which includes the macOS system make, as [R-73](#r-73) says, and the shell is POSIX `sh`. A recipe uses no `.ONESHELL`, no Make 4 function, and no shell-script wrapper. This applies to both. `r-project-setup` owns the rule, and `r-shell` and `r-github-pipeline` follow it. |
| <a id="r-23"></a>R-23 | Makefile include and project targets | in force | The root Makefile includes `project.mk` or `sdlc.mk` from `.claude/skills/` before any target. It defines no target of the Make contract again, because Make is the only interface. A project changes such a target only through its command variable and adds its own targets after the include. There is no root copy of `project.mk` or `sdlc.mk`. This applies to a product repository. `r-project-setup` owns `project.mk`, and `r-github-pipeline` owns `sdlc.mk`. |
| <a id="r-45"></a>R-45 | Make contract | in force | `r-project-setup` is the Make contract. Make is the only interface, and a target does the same thing locally and in CI. A laptop-only command gets its own name, `dev` or `verify`. A repository that uses Make and does not publish through GitHub installs only this skill. This applies to a product repository, and `r-project-setup` owns the contract. |
| <a id="r-87"></a>R-87 | Setup mode and report mode | in force | Setup mode writes only what is missing or off the contract and leaves a target that the project already filled in. Report mode fills the contract-report skeleton in the reply and writes nothing, and a request for both runs report mode first. Setup mode adds no `sdlc.mk`, workflow, or `v*` tag. This applies to a product repository. |
| <a id="r-88"></a>R-88 | Command variables | in force | The project sets the command variables of the contract before the include, such as `TEST_CMD` and `LINT_CMD`, and an empty one makes its target fail. A project with nothing to run sets the variable to `true`. Setup mode sets a variable only when it is empty and the toolchain is already in the project. This applies to a product repository. |
| <a id="r-89"></a>R-89 | Host tools in a recipe | in force | A recipe that runs a toolchain on the host is off the contract, and setup mode rewrites it to the command variable. A recipe may call `git`, `podman`, and the tools of POSIX `sh`, as [R-75](#r-75) says. Only the target `host-tools` of [R-129](#r-129) calls `python3` and `go` to install the tools of host mode. The host needs only `make`, `git`, and `podman`. This applies to a product repository. |
| <a id="r-90"></a>R-90 | Targets of the Make contract | in force | Setup installs EditorConfig, one formatter, one linter, unit tests, and one integration entry, all as Make targets. It adds `coverage` and `test-changed` when they are missing. `test` leaves integration tests out, and `integration` is the only integration entry. `docs` and `login` exist only when their conditions hold. This applies to a product repository. |
| <a id="r-91"></a>R-91 | Login and registry | in force | `PUBLISH_IMAGE` and `login` exist when an image is published. `login` runs `podman login` with `REGISTRY_USER` and `REGISTRY_TOKEN`, and `REGISTRY` defaults to `ghcr.io`. This applies to a product repository. |
| <a id="r-92"></a>R-92 | Makefiles of skills and old board | in force | `skills.mk` runs APM in an image through `skills-install`, `skills-update`, and `apm`, and `old-board.mk` has `old-board`, which fails when a path of the old board exists. This applies to a product repository. |
| <a id="r-75"></a>R-75 | Make and Podman are the only interface | in force | A person and an agent type only `make <target>` and Git commands. The host needs only GNU Make 3.81 or newer, Git, and Podman. Make runs every other tool in a Podman image, on a laptop and in CI. On a machine without Podman, host mode of [R-129](#r-129) runs the same tools from `PATH`. A typed `tail` or `grep` only shortens or searches output and writes no file. This applies to both. The general rules of [R-76](#r-76) state the rule, and `r-project-setup` owns the makefiles that carry it. |
| <a id="r-2"></a>R-2 | Full suite and changed tests | in force | `make test` is the full suite. `make test-changed` runs only the tests whose coverage includes a file in the diff. It reads the coverage map that `make coverage` writes, not a hand-kept list. A green `test-changed` does not replace `make test`, and CI runs `make test`. This applies to both. `r-project-setup` owns the targets, `r-project-report` ships the selection for each language, and `r-develop` and `r-review` run them. |
| <a id="r-125"></a>R-125 | One docs renderer | in force | `make docs` renders `docs/` to HTML in `build/docs` with the one renderer `scripts/render_docs.py` of `r-project-setup` when `RENDER_DOCS` is 1. A project keeps no renderer of its own. It sets `DOCS_OPTIONS` for options such as the page language. The renderer uses the Python standard library only. This applies to a product repository, and `r-project-setup` owns the renderer. |
| <a id="r-127"></a>R-127 | Gate stamp and pre-push hook | in force | `make gates` runs the six gates in order and, only when all pass, writes `build/gates.ok` with the tree id of the working tree. The id is computed from a temporary copy of the index, so the staging area stays as it is, and it equals the tree of a commit of that content. The git hook `pre-push` compares the stamp with the tree of each pushed commit, not with the files on disk. It refuses the push when the stamp is missing, or when the trees differ in a file outside `BOARD_FILES`. So a partial commit fails, and the close commit of `r-release` passes. `make setup`, `make gates`, and `make test-changed` install the hook, so the first gate run in a fresh clone installs it. A guard hook refuses `--no-verify` from an agent, as [R-124](collection.md#r-124) says. The install replaces only a hook that it wrote, and prints and skips any other. `git push --no-verify` is the only bypass. The hook is a git hook, so it works with any agent, as [R-17](collection.md#r-17) says. This applies to a product repository and to this collection, and `r-project-setup` owns the rule. |
| <a id="r-129"></a>R-129 | Host mode for a machine without Podman | in force | With `TOOLS=host`, Make runs each shared tool and each language tool from `PATH` in place of Podman, so a cloud session runs every gate through Make. `make host-tools` installs the pinned shared tools into `build/host-tools`, and `make setup` runs it in host mode. Podman stays the default, and the image targets still need it. A command variable uses a tool variable such as `$(RUFF)`, not a literal `podman run`, so host mode reaches it. This applies to both, and `r-project-setup` owns the rule. |
