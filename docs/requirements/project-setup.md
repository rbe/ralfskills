| <a id="r-60"></a>R-60 | Entry file template | in force | `r-project-setup` has the template of the entry file, `templates/CLAUDE.md`. Setup mode writes `CLAUDE.md` from the template when the file is missing, and fills each bracket from the project and from `docs/skill-index.toon`. When the file exists, setup mode adds each paragraph of the template that is missing. If the file has no `<general_rules>` block, setup mode adds the section `## General rules` before the communication contract. If the block differs from the template, setup mode replaces the block. Setup mode then deletes each sentence outside the block that the block states, names each deleted sentence in the reply, and keeps the other text. The skills of the collection are the stages `r-plan`, `r-develop`, `r-review`, and `r-release`; the other skills `r-record`, `r-project-report`, `r-project-setup`, `r-github-pipeline`, `r-migrate-docs`, `r-onboard`, `r-system-state-report`, `r-board-merge-report`, `r-board-merge`, `r-skills-review`, `r-component-upgrade`, `r-upgrade-go-components`, `r-upgrade-java-components`, `r-upgrade-node-components`, and `r-upgrade-python-components`; the language skills `r-node`, `r-python`, `r-shell`, `r-jvm`, and `r-go`; and the subskills `r-security`, `r-privacy`, `r-ux-ui-design`, `r-api-design`, `r-observability`, and `r-performance`. This list is the one list of the skills, and each other row points here. The entry file names the stages and where a request starts, the other skills (`r-record`, `r-project-report`, `r-project-setup`, and each installed one of `r-onboard`, `r-migrate-docs`, `r-github-pipeline`, `r-system-state-report`, `r-board-merge-report`, `r-board-merge`, `r-skills-review`, `r-component-upgrade`, and the `r-upgrade-<language>-components` of each installed language), the installed language skills and subskills, each project skill, how the project ships, the general rules, and the communication contract. The general rules say where each record is kept. Setup mode asks the owner how the project ships before it copies a Makefile template, and it sets the build command of a binary with that answer. Setup mode runs `make toon` before it fills the brackets. The contract report has a row for the entry file. The template is the one source of that text for a product repository. This applies to a product repository. `r-project-setup` owns the template. |

This applies to this collection and to a product repository. `r-project-setup` owns the template. |

The target fails when a `SKILL.md` or a reference file of an installed skill names a path under `skills/r-*/` or `.claude/skills/r-*/` that does not exist, or names `make <target>` inside backticks or a fenced block for a target that no makefile of the repository defines. Each finding has the file, the line, and the name. Unit tests with fixture directories check the script, and one test runs it on this collection. This applies to both. `r-project-setup` owns the target. |

No stage skill repeats the rule. A unit test checks the sentence in both files and that no `SKILL.md` repeats it. This applies to this collection and to a product repository. `r-project-setup` owns the template. |
| <a id="r-76"></a>R-76 | General rules, tag shape, and reference files | in force | The rules that hold for every skill stand once, in the `<general_rules>` block of `CLAUDE.md` and of `templates/CLAUDE.md` in `r-project-setup`. The block has the parts Interface, Start of a task, Board, and Gates. Each `SKILL.md` has the line ``The general rules in `CLAUDE.md` apply.`` as the first line of its body, and it repeats no general rule. The description in the frontmatter says what the skill does and then when to use it, in the third person. A unit test checks the line, the tags, and the names of the reference files. `CLAUDE.md` has at most 966 words and the template has at most 1036 (`wc -w`), and a unit test checks both limits. A rule that only one skill applies stands in that skill. The general form of the `make -f` rule before the Make include is in `r-project-setup`, a skill that runs before the include names its own makefile in its step, and the rule that `r-onboard`, `r-migrate-docs`, and setup mode open no history file is in `r-record`. This applies to this collection. Each skill owns its files. `r-project-setup` owns the template of the entry file. |

| <a id="r-71"></a>R-71 | Shared contract targets | in force | `r-project-setup` has `contract.mk` with the targets of the Make contract. `project.mk` and the `sdlc.mk` of `r-github-pipeline` both include it, so a project that switches from `project.mk` to `sdlc.mk` keeps `setup`, `build`, `test`, `format`, `lint`, and `coverage`. This applies to a product repository. `r-project-setup` owns `contract.mk`. `r-github-pipeline` owns the rest. |
| <a id="r-73"></a>R-73 | Doctor and src layout | in force | `make doctor` checks GNU Make 3.81 or newer, Git, and `podman info`, and, when the project has a workflow, the remote `origin`. It prints `ok` or `FAIL` with the fix, and it stops on a `FAIL`. `doctor.mk` makes `doctor` the first prerequisite of `setup`. `make setup` therefore runs `doctor` before `toon` and before its recipe, also in the Node and Gradle templates. A unit test checks the prerequisite and the order of the includes. | <a id="r-9"></a>R-9 | Existing formatter and linter | in force | The formatter and the linter are existing tools the language skill names. Do not write a linter. Do not write a formatter. | <a id="r-12"></a>R-12 | Diff coverage | in force | `coverage` writes `build/coverage/diff.md` through diff-cover, for the lines this change touched. diff-cover runs in `DIFF_COVER_IMAGE`, an image that has git and Python. A repository-wide percentage used as the result is a finding. A missing report is not run, and the finding says why. The test job uploads this file, not a repository-wide percentage. | <a id="r-11"></a>R-11 | Help is the default goal | in force | `help` is the default goal. `make` with no arguments prints the same help as `make help`. `.DEFAULT_GOAL` is `help`. The line `# help-group: <Name>` puts the targets that follow it in that group. The first line of each makefile starts in the group `Project`, so a target of the product Makefile is listed there. Every makefile of this collection has the marker before its first target with a `##` comment, and one more marker where the group changes: `Gates` for `setup`, `build`, `test`, `editorconfig`, `format`, `format-fix`, `lint`, `integration`, `coverage`, `docs`, `test-changed`, `check-docs`, and `ci`, `Board` for `project-report`, `old-board`, `old-board-delete`, `board-numbers`, and the targets of `index.mk`, `Delivery` for `version`, `check-tag`, `publish-tags`, `report`, `login`, the image targets, the cleanup targets, `ci-status`, and the pull request targets, and `Tools` for `help`, `py`, `doctor`, `podman-start`, `skills-install`, `skills-update`, `apm`, `gh-image`, and the language targets of [R-122](collection.md#r-122). | <a id="r-44"></a>R-44 | Make 3.81 and POSIX sh | in force | Recipes run on GNU Make 3.81 or newer, including the macOS system make, as [R-73](#r-73) says, and the shell is POSIX `sh`. | <a id="r-75"></a>R-75 | Make and Podman are the only interface | in force | A person and an agent type only `make <target>` and Git commands, such as commit, push, merge, tag, log, and diff. The host needs GNU Make 3.81 or newer, Git, and Podman. It needs no APM, no GitHub CLI, no jq, no Python, no Node, no Go, no Gradle, and no Homebrew. Make runs every other tool in a Podman image, on a laptop and in CI. No recipe calls a host tool other than `git` and `podman`. The tools of POSIX `sh`, such as `sed`, `awk`, `grep`, `find`, and `tar`, are part of the shell. A person and an agent may type such a tool, such as `tail` or `grep`, only to shorten or search output, and it writes no file. A unit test reads every `*.mk`, every `templates/Makefile.*`, and the root `Makefile`, and fails on a host call of gh, jq, brew, curl, apm, pip, npm, npx, node, python, gradle, or go. APM runs in `APM_IMAGE` with the version `APM_VERSION`, behind `make skills-install`, `make skills-update`, and `make apm ARGS='...'`. The GitHub CLI runs in the image that `make gh-image` builds, and it reads `GH_TOKEN` or `GITHUB_TOKEN` from the environment. `make ci-status`, `make pull-request`, and `make pull-request-merge` use that image, as [R-99](github-pipeline.md#r-99) says, so an agent reads the CI result and opens a pull request with no host `gh`. `pull-request` and `pull-request-merge` call `gh api` with REST routes only, because the GraphQL API is closed in some networks. The smoke check of the Node pipeline template runs curl in `CURL_IMAGE`. `make old-board` and `make old-board-delete` test and delete the old board. `make doctor` checks the host, as [R-73](#r-73) says. `make podman-start` starts the Podman machine on macOS and creates it when none exists, and the fix line of `doctor` names it. If the Makefile has no include yet, a target runs as `make -f .claude/skills/<skill>/<file>.mk <target>`. `report.mk` of `r-project-report` and `index.mk` of `r-record` include `podman-python.mk` when they run alone. If no target runs the command that the work needs, `r-project-setup` adds the target. The first start is the one exception: a project has no Makefile before the skills are installed, so install uses the `podman run` line of the README, as [R-16](collection.md#r-16) says. No skill repeats that line. This applies to both. The general rules of [R-76](#r-76) state the rule for every skill. `r-project-setup` owns `skills.mk`, `old-board.mk`, `doctor.mk`, and `tools.mk`. `r-migrate-docs` owns `migrate.mk`. `r-github-pipeline` owns the image of the GitHub CLI. |
| <a id="r-2"></a>R-2 | Full suite and changed tests | in force | `make test` is the full suite. `make test-changed` runs only the tests whose coverage includes a file in the diff. A green `test-changed` does not replace `make test`. `test-changed` is not a CI target. CI runs `make test`. This applies to both. `r-project-setup` owns the targets. `test-changed.mk` in `r-project-setup` holds the target. `project.mk` and `sdlc.mk` include it, so a project has the target with either include. `r-project-report` ships the selection for Python, Node, Go, and the JVM. For Go, `go_cover_map.py` reads the coverage profiles. For Node, `node_cover_map.py` reads the V8 coverage files that Node writes when `NODE_V8_COVERAGE` is set. A test class covers each source file that ran in its JVM, and the Gradle test task sets `forkEvery = 1`. `changed_tests.py --print` names the chosen tests, and the project's runner runs them. The recipe prints the chosen tests before it runs them. The Node map is exact with `node --test` and with Jest. A runner that shares a process between tests selects more tests, never fewer. The workers of Vitest write no V8 coverage. A Vitest project sets `TEST_CHANGED_CMD` to `vitest related --run` with the changed files, and Vitest selects from its module graph. That is the one selection that is not coverage, and the project records it as a requirement row. A change to a file no test loads selects no test. Empty, `TEST_CHANGED_CMD` fails the target and names the variable. `r-develop` and `r-review` run them. |
