# Requirements of r-github-pipeline

The rows that the skill `r-github-pipeline` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-42"></a>R-42 | What a shipment contains | in force | A shipment is a binary, a container image, or a library package, as [R-57](release.md#r-57) says. The image copies named files, not the work tree. `r-github-pipeline` has the four Containerfile templates `Containerfile.node`, `Containerfile.gradle`, `Containerfile.python`, and `Containerfile.golang`, and the templates `containerignore` and `gitignore`. `.containerignore` keeps out `.git`, `.github`, `.claude/`, `apm_modules/`, `CLAUDE.md`, `docs/`, `build/`, `node_modules`, `data/`, `.env`, `.env.*`, and `*.tar`. Example data ships only from `examples/` when the path and the name say it is an example. Skills, the entry file, and development files stay out. `.claude/skills/` is committed so Make can include it, and the image still excludes `.claude/`. `.gitignore` keeps build output, image tars, `data/`, and `.env` out of git. A Make-only repository that ships a binary follows the same limit. This applies to a product repository. `r-github-pipeline` owns the image rules. `r-project-setup` points at them and states the limit for a binary. The other skills point at `r-project-setup`. |
| <a id="r-46"></a>R-46 | GitHub delivery contract | in force | `r-github-pipeline` is the delivery contract for a repository that publishes through GitHub. No file of `r-github-pipeline` names `BUGS.md`, `WAVES.md`, or `FEATURES.md`. A Make-only repository does not install this skill, as [R-45](project-setup.md#r-45) says. The files it checks are `docs/pipeline-rules.md`, `Containerfile`, `.containerignore`, `.gitignore`, and `Makefile`. Setup mode writes only what is missing or off the contract. Report mode writes no project file and does not run a publish target or a cleanup target. Setup mode names a second workflow file and does not delete it. The contract test fails when the workflow, the include, retention, or a `run` step leaves this contract. Do not weaken that test. Node 24 belongs to the Node template only. A Gradle project uses the JDK in its template. No shell script is shipped. This applies to a product repository that installs the skill. `r-github-pipeline` owns the contract. `r-release` invokes it as [R-22](plan.md#r-22) says. |
| <a id="r-93"></a>R-93 | Workflow and jobs | in force | There is one pipeline workflow, `.github/workflows/ci.yml`, named `CI`. [R-117](#r-117) says when a second workflow, `publish-client.yml`, exists. `setup` runs first, then `build` and `test` beside each other, and `docs` only when the repository renders docs, then `publish-container` and, when the project releases a JAR, `publish-github`, then `report`. `docs` is absent when there is nothing to render. `report` is last and uses `if: ${{ !cancelled() }}`. A step is `actions/checkout`, an artifact upload or download, or `run: make <target>`. The runner label is `ubuntu-26.04`. The `setup` job runs `make cleanup-actions-artifacts` first. The test job runs `make editorconfig`, `make format`, `make lint`, `make test`, `make integration`, and `make coverage`. The publish job runs `make login`, then `make publish-container`, then `make cleanup-container-versions`. `publish-container` writes the version to `build/publish-version.txt`. `make report` writes `build/report/index.md`. Each job uploads `report-<job>` with `build/logs` and `build/summaries`. Every upload sets `retention-days`: 1 for intermediates, 14 for `report` and rendered docs. The workflow `env` holds `IMAGE` and `SDLC_DEFAULT_BRANCH`. This applies to a product repository that installs the skill. |
| <a id="r-94"></a>R-94 | Triggers and permissions | in force | `publish-*` runs when `workflow_dispatch` selects that job, and on a push to the default branch only when the repository variable `AUTO_PUBLISH` is `true`. It needs `build` and `test` to have succeeded. There is no `pull_request` trigger and no tag trigger in `ci.yml`. After tagging `vX.Y.Z`, start the publish job from the Actions tab. In-progress runs are cancelled only when the push is not the default branch. Permissions are `contents: read` at the top, `actions: write` on `setup`, `packages: write` on `publish-container`, and `contents: write` on `publish-github`. This applies to a product repository that installs the skill. |
| <a id="r-95"></a>R-95 | Version and image tags | in force | `make version` prints `MAJOR.MINOR.PATCH-<run>` from the nearest strict `vMAJOR.MINOR.PATCH` tag plus `GITHUB_RUN_NUMBER`. It fails when that tag is missing, a nearer pre-release tag is closer, or the run number is missing. `make version PRINT=tag` prints the tag. [R-57](release.md#r-57) says who creates the `v*` tag. `publish-tags` adds `latest` only on the default branch or when `GITHUB_REF` is unset. There is no `edge` tag, no `sha` tag, and no bare version tag. This applies to a product repository that installs the skill. |
| <a id="r-96"></a>R-96 | Cleanup targets | in force | On the default branch, cleanup keeps the published version and the next-lower run number on the same line, does not delete a version that still wears `latest` or any tag other than `MAJOR.MINOR.PATCH-<run>`, and deletes nothing in CI off the default branch. A missing package is an empty list. `KEEP_VERSIONS` defaults to 2. `cleanup-github-releases` never deletes a name that is not `MAJOR.MINOR.PATCH-<run>`. `cleanup-actions-artifacts` deletes this repository's artifacts older than one hour, except `report`, `docs`, and the current run. `cleanup-container-versions` and `cleanup-github-releases` work at any time, with or without `DRY_RUN=1`, and need no git tag and no `GITHUB_RUN_NUMBER`. The kept version is `PUBLISHED_TAG`, else the content of `build/publish-version.txt`, else the newest rolling version by `created_at` of the list from GitHub. A list with no rolling version deletes nothing and exits 0. A given tag that is not exactly one version in the list stops the target, and the message names `PUBLISHED_TAG` or `build/publish-version.txt`. `DRY_RUN=1` prints the deletions and deletes nothing. Without `DRY_RUN=1` a cleanup deletes, also on a laptop where `GITHUB_REF` is unset. This applies to a product repository that installs the skill. |
| <a id="r-97"></a>R-97 | Divergences from the pipeline rules | in force | `docs/pipeline-rules.md` is copied from the skill template when it is missing. An existing "This repository" section and "Divergences" section stay as written. A divergence is the rule, what differs, and why. Allowed divergences are a JAR or binary `publish-github`, no `docs` job, no `publish-container` for a library, Gradle building the image from the tested JAR, and laptop targets no job calls. A second name for the same target, logic in the YAML, Docker, an upload without `retention-days`, publishing on a tag push or from a branch, a publish that skips `test`, and a version that does not come from `version` are not divergences. This applies to a product repository that installs the skill. |
| <a id="r-98"></a>R-98 | Targets and variables of sdlc.mk | in force | `sdlc.mk` holds `version`, `publish-tags`, the cleanups, `report`, `help`, `ci`, `ci-status`, `pull-request`, and `pull-request-merge`. The project sets `IMAGE`, `PACKAGE`, and `KEEP_VERSIONS` before the include, and may set `SDLC_JOBS`, `SDLC_CI`, and `SDLC_KEEP_ARTIFACTS`. `ci` runs `SDLC_CI` in order and does not publish. `$(call SDLC_LOG,job,_job)` writes the log of a publish job to `build/logs` and a failed summary when the job fails. The contract targets write no log. The command variables of the Node and Gradle templates write their summary to `build/summaries`. A recipe that must not run under `make -n` calls `$(THIS_MAKE)`. This applies to a product repository that installs the skill. |
| <a id="r-99"></a>R-99 | CI status and pull request targets | in force | `make ci-status` prints the result of the CI run for `HEAD`, or for `SHA=<sha>`, and exits non-zero when the run failed, did not finish, or does not exist. `WAIT=1` waits for the end. `make pull-request` opens a pull request from the current branch to `DEFAULT_BRANCH`, and `make pull-request-merge` merges it when its checks passed. All three run the GitHub CLI in the `gh-image` container, with the repository from `OWNER` and `NAME`, because that image has no Git. `ci-status` passes `-R owner/name`. `pull-request` and `pull-request-merge` call `gh api` with REST routes. All three stop with a message when neither `GH_TOKEN` nor `GITHUB_TOKEN` is set. This applies to a product repository that installs the skill. |
| <a id="r-115"></a>R-115 | Host ports above 1024 | in force | A container may use a standard port inside, such as 443. A host binding of a published port uses a user port above 1024, for example 8443, so no root privileges are needed. In `templates/Makefile.node`, `PORT` is the port inside and `HOST_PORT` is the port of the host. `run` publishes `127.0.0.1:$(HOST_PORT):$(PORT)` and fails when `HOST_PORT` is 1024 or lower. No template of a skill publishes a host port of 1024 or lower. This applies to a product repository that installs the skill. `r-github-pipeline` owns this rule. |
| <a id="r-117"></a>R-117 | Publish the client package | in force | A project with `client/package.json` has `.github/workflows/publish-client.yml`, copied from `templates/publish-client.yml`. The workflow is named `Publish client`. It runs on `workflow_dispatch` and on a tag `client-v*`. It has `contents: write` and `packages: write`, and it does not call `ci.yml` or build the image. The version is the version of `client/package.json`. The workflow does not invent a version: a tag that is not `client-v<version>` fails the run, and a version that is not `MAJOR.MINOR.PATCH` fails the run. It runs `npm ci`, `npm test`, and `npm pack`, creates the GitHub Release `client-v<version>` with the tarball, and publishes the package to `https://npm.pkg.github.com` under the scope of the repository owner. A second run of the same version creates no second release and no second package version. The workflow is a divergence that `docs/pipeline-rules.md` names. This applies to a product repository that installs the skill. `r-github-pipeline` owns this rule. |
| <a id="r-119"></a>R-119 | Smoke check of a web image | in force | The smoke check of `templates/Makefile.node` starts the image and runs two checks through curl in `CURL_IMAGE`. The API path `SMOKE_PATH` returns a body that holds `SMOKE_NEEDLE`. The page at `/` holds `SMOKE_PAGE_NEEDLE`, which defaults to `id="root"`, the root element of a single-page app. An empty `SMOKE_PAGE_NEEDLE` turns the page check off, for an app with no page. A failed check fails `make build`. This applies to a product repository that installs the skill. `r-github-pipeline` owns this rule. |
| <a id="r-120"></a>R-120 | Check a tag before it is pushed | in force | `make check-tag TAG=vX.Y.Z` runs before the owner pushes a `v*` tag, and it writes nothing. It exits non-zero when `TAG` is not set, is not `vMAJOR.MINOR.PATCH`, already exists, is not newer than every strict `v*` tag, or when `HEAD` is not the tip of the default branch. A pre-release tag fails the format check. A tag that passes is a tag that `make version` accepts. `r-release` creates no tag, as [R-57](release.md#r-57) says. This applies to a product repository that installs the skill. `r-github-pipeline` owns this rule. |
| <a id="r-121"></a>R-121 | Only a human publishes a large artifact by default | in force | By default only a human publishes a large artifact, such as a container image or a JAR release, to a registry, with `workflow_dispatch`. The reason is the GitHub quota of storage, artifacts, and minutes. A project opts in to a publish on every push to the default branch with the repository variable `AUTO_PUBLISH` set to `true`. In the workflow templates, the `if:` of each `publish-*` job is `(push && default branch && vars.AUTO_PUBLISH == 'true') || inputs.job == '<job>'`. Every other push publishes nothing, and a tag push publishes nothing. No Make target reads `AUTO_PUBLISH`, and `SDLC_CI` has no publish target, so `make ci` publishes nothing. `publish-client.yml` runs only on a tag or `workflow_dispatch`, which a human starts, and its npm package is small, so it has no `AUTO_PUBLISH`. This applies to a product repository that installs the skill. `r-github-pipeline` owns this rule. |
