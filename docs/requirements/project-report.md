# Requirements of r-project-report

The rows that the skill `r-project-report` owns. `collection.md` says what the status means.

| Id | Title | Status | Statement |
| --- | --- | --- | --- |
| <a id="r-3"></a>R-3 | Generated project report | in force | `make project-report` writes `build/project-report.md`. The file has three parts: the requirements-to-tests map, the architecture review, and the development review. `r-review` stops when the target fails, when a part is missing, or when the file was hand-edited. A test with no id fails the target. A test whose id is not a requirement id fails the target. On a product repository a requirement id is an ADR id or the id of a requirement row in force. The map does not list a roadmap row or a planned row. The two reviews list them. The reviews are lists, not a judgement. On a product repository, the two reviews are drawn from the ADRs, the roadmap, the planned requirement rows, and the checks in `r-plan`, `r-develop`, `r-review`, `r-release`, and `r-project-setup`. When the repository keeps `docs/requirements/` and has no ADR file, a requirement id is an in force row of a file there, and the map links each id to the file of its row. The architecture review then holds the checks in `r-plan` and `r-review`. The development review holds the planned rows and the checks. When the repository has ADR files, the target keeps the product ADR behaviour. This applies to both, with that switch. `r-project-report` owns the target. `r-review` runs it. |
| <a id="r-63"></a>R-63 | Test ids in every language | in force | In a Python test, the `id:` line is in the docstring of the test. In a JavaScript, TypeScript, Java, Groovy, Kotlin, or Go test file, the `id:` line is a comment, as `// id: R-1`, and the file is the proof. One file may have several such lines. A test file is a file whose name ends with `.test` or `.spec` before a JavaScript or TypeScript extension, with `Test`, `Tests`, `Spec`, or `IT` before a Java, Groovy, or Kotlin extension, or with `_test.go`. A file under `.claude/`, `apm_modules/`, `node_modules/`, `build/`, `dist/`, `.gradle/`, or `.venv/` is not a project test. APM keeps its copy of the collection in `apm_modules/`. This applies to both. `r-project-report` owns the reading. |
| <a id="r-64"></a>R-64 | Project report target in a product | in force | `report.mk` beside the `r-project-report` skill sets `PROJECT_REPORT_CMD` to the installed script when the project did not set it. `project.mk` and `sdlc.mk` include that file when the skill is installed. `report.mk` owns the `project-report` target for both includes. Without the skill, `contract.mk` of `r-project-setup`, which `project.mk` and `sdlc.mk` include, has a `project-report` target. It runs `PROJECT_REPORT_CMD` when the project set it. When the variable is empty, it fails and names the variable. This applies to a product repository. `r-project-report` owns `report.mk`. |
