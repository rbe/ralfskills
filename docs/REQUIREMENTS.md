# Requirements

Each requirement is one row this skill set must fulfill. The list is enough to reimplement the skill set. The index lists the id and the title. A sentence that begins with `This applies to` says where the row holds: this collection, a product repository, or both.

## Collection shape

| Id | Title | Statement |
| --- | --- | --- |
| <a id="r-16"></a>R-16 | APM skill package | ralfskills is an APM skill collection. Each skill is one directory `skills/<name>/SKILL.md`. There is no root `SKILL.md`. Install the set with the one `podman run` line of the README, which runs `apm install` in an image, or install selected skills by name with `make apm ARGS='...'`. The `apm.yml` of a project needs `name` and `version`. A project commits `.claude/skills/`, `apm.yml`, and `apm.lock.yaml`, because its Makefile includes files from `.claude/skills/`. The skills in the set are `plan`, `develop`, `review`, `release`, `record`, `migrate-docs`, `project-setup`, `github-pipeline`, `project-report`, `security`, `privacy`, `ux-ui-design`, `api-design`, `node`, `python`, `shell`, `jvm`, `go`, `onboard`, and `system-state-report`. This applies to this collection. APM is the installer. |
| <a id="r-17"></a>R-17 | Install path and agent-agnostic text | Installed skills live under `.claude/skills/`. That is the APM target `claude`. Skill text is agent-agnostic. A skill file does not name Cursor, and it does not mention `.agents/`. This applies to this collection and to the skills a product repository installs. |
| <a id="r-18"></a>R-18 | CLAUDE.md is the entry file | `CLAUDE.md` is the only entry file. The repository has no `AGENTS.md`. The entry file names the stages, `record`, `project-report`, `project-setup`, and `github-pipeline`, then the language skills and the subskills, and it says a project skill is an extra name listed there. It holds the general rules, as [R-76](#r-76) says. This applies to this collection and to a product repository that uses the skills. `migrate-docs` is the skill that removes an old `AGENTS.md`. [R-60](#r-60) says where a product repository gets its entry file. |
| <a id="r-60"></a>R-60 | Entry file template | `project-setup` has the template of the entry file, `templates/CLAUDE.md`. Setup mode writes `CLAUDE.md` from the template when the file is missing, and fills each bracket from the project and from `docs/skill-index.toon`. When the file exists, setup mode adds each paragraph of the template that is missing. If the file has no `<general_rules>` block, setup mode adds the section `## General rules` before the communication contract. If the block differs from the template, setup mode replaces the block. Setup mode then deletes each sentence outside the block that the block states, names each deleted sentence in the reply, and keeps the other text. The entry file names the stages and where a request starts, the installed language skills and subskills, each project skill, how the project ships, the general rules, and the communication contract. The general rules say where each record is kept. Setup mode asks the owner how the project ships before it copies a Makefile template, and it sets the build command of a binary with that answer. Setup mode runs `make toon` before it fills the brackets. The contract report has a row for the entry file. The template is the one source of that text for a product repository. This applies to a product repository. `project-setup` owns the template. |
| <a id="r-4"></a>R-4 | Skill name matches directory | The `name` in a skill's frontmatter matches its directory. `make toon` reads every `SKILL.md` in the installed set and fails when a name does not match. This applies to this collection and to every installed skill. `record` owns the check. |
| <a id="r-65"></a>R-65 | Frontmatter is YAML | APM reads the frontmatter of a `SKILL.md` as YAML and refuses to install a collection when one skill does not parse. A frontmatter value is one YAML string. It has no colon followed by a space and no ` #`, or it is quoted. `make toon` fails when a value breaks this rule. The APM install of this collection into a sample project is the check that the collection installs. This applies to this collection and to a product skill. `record` owns the check. |
| <a id="r-52"></a>R-52 | Product skills stay in the product | A product skill stays in the product repository and is named in that repository's `CLAUDE.md`. Product catalogues stay in their repositories. Examples are a route list, tokens, a type scale, and a component catalogue. This collection does not ship `.apm/agents`. It has no user-facing orchestrator. It has no implement, record, or verify persona. `record` here is a skill, not a persona. This applies to this collection. A product repository owns its own extra skills. |
| <a id="r-76"></a>R-76 | General rules, tag shape, and reference files | The rules that hold for every skill stand once, in the `<general_rules>` block of `CLAUDE.md` and of `templates/CLAUDE.md` in `project-setup`. The block has the parts Interface, Start of a task, Board, and Gates. It stands before the communication contract, and it is the same text in both files. Each `SKILL.md` has the line ``The general rules in `CLAUDE.md` apply.`` as the first line of its body, and it repeats no general rule. The body of a `SKILL.md` is XML tags and has no Markdown heading. The tags are `purpose`, `inputs`, `steps`, `rules`, `output`, `references`, `example`, `questions`, `checks`, and `mode` with a `name`. A tag stands alone on its line and is closed. Only `steps` and `rules` nest, and only in a `mode`. A subskill has `questions` and `checks`. `project-setup` has its nine quality checks in a top-level `checks` block. The project report reads that block, and the first `steps` block of each stage. A `SKILL.md` holds what an agent needs on every run. A table, a variable list, a sample, or a rule that holds only under a condition is in `skills/<name>/references/<topic>.md`, one level deep. The `SKILL.md` names each of its reference files with the condition under which the agent reads the file. The description in the frontmatter says what the skill does and then when to use it, in the third person. A unit test checks the line, the tags, and the names of the reference files. `CLAUDE.md` has at most 705 words and the template has at most 780 (`wc -w`), and a unit test checks both limits. A rule that only one skill applies stands in that skill. The rule on `make -f` before the Make include is in `project-setup`, and the rule that `onboard`, `migrate-docs`, and setup mode open no history file is in `record`. This applies to this collection. Each skill owns its files. `project-setup` owns the template of the entry file. [D-15](DECISIONS.md#d-15) records the choice. |

## Stages

| Id | Title | Statement |
| --- | --- | --- |
| <a id="r-19"></a>R-19 | Four numbered stages | The stage skills are `plan`, `develop`, `review`, and `release`, in that order. Each has one `<steps>` block, a short numbered list of its work in order. A duty of a stage is a numbered step, not only a paragraph. The last step asks `record` to write the history section. The frame that every skill repeated before is in the general rules, as [R-76](#r-76) says: the stop on the old board, `record` before an id or a document, and no later step after a stop. `record` has the modes write and close. Write mode starts with the id check. Close mode starts with the check that Plan, Develop, and Review were written. This applies to both. Each named skill owns its own list. |
| <a id="r-20"></a>R-20 | record writes ids and documents | `record` is the only writer of ids and of board documents. A stage calls `record` by name before any id or any document. A write that skips `record` fails that step. `record` does not delegate the id check to another skill. The last step fails when the history file is missing a Plan, Develop, Review, or Release heading. A skill that is not a stage adds one line that names the skill to the section of the stage that runs, so a language skill adds its line under Develop. Such a skill opens no history file, and it adds no line when no history file is open. The general rules state this once, and no skill repeats it. This applies to both. `record` owns the write. |
| <a id="r-21"></a>R-21 | Old board stops other skills | The old board is `docs/BUGS.md`, `docs/WAVES.md`, `docs/FEATURES.md`, `docs/bugs/`, `docs/waves/`, and `docs/features/`. `make old-board` prints each of these paths that exists and fails when one exists. An empty directory counts. The general rules tell an agent to run the target before the first skill. If the target fails, the only skill is `migrate-docs`. `record` is the one skill `migrate-docs` may invoke while those paths still exist. `onboard` runs the target in its own step and invokes `migrate-docs` itself. No `SKILL.md` other than that of `migrate-docs` names a path of the old board, and a unit test checks this. This applies to both. `migrate-docs` is the skill that may continue. |
| <a id="r-49"></a>R-49 | Plan closes a slice | `plan` grills a change before editing. Use it when a request is new, vague, or would change a decision, an ADR, the roadmap, or a proposal. A request that already names a source file, a failing test, or a known issue is `develop`. Work runs in this order. Run `make toon` and read the board for this repository. For each skill-index row whose `kind` is `check`, in that index order, read the skill and ask its questions. Ask one question, then wait. Before the slice closes, `plan` asks what the result looks like: the output or the interface, the empty case, and the error case. Stop when the slice is one sentence, with an out-of-scope line. Do not ask a question an accepted ADR, a Decided entry, or an open proposal already answered. Then name the boundary and the pattern, then evaluate architecture with the words in [R-14](#r-14), then ask for an ADR as [R-53](#r-53) says, then invoke `project-setup` only as [R-22](#r-22) says, then stop when the slice needs a language the skill index does not list. This applies to a product repository, and to this collection when someone plans a change here. `plan` owns the grill. |
| <a id="r-7"></a>R-7 | Boundary and pattern | Before the slice closes, `plan` names who owns state, what may call what, and the pattern. When the boundary keeps the slice out of a package, `plan` names each existing function there that the slice needs, and says whether the slice moves it, exports it, or repeats it. That is step 4, after the one-question grill. Architectural patterns are part of that grill. Stop when that sentence is missing. `review` fails the change when code ignores the pattern `plan` named. `plan` chooses the pattern. `review` does not name a different one. Clean Code catalogues and pattern catalogues are not separate skills. This applies to both. `plan` owns the sentence. `review` owns the check. |
| <a id="r-14"></a>R-14 | Costly choices wait | `plan` step 5 is this text, and only this text, immediately after the boundary step. The words are: Evaluate architecture, scalability, and code quality against the constraints of this system. Prefer the smallest design that stays operable and maintainable. When a choice is expensive to reverse, name the options, recommend one, and wait. Otherwise implement it in small modules. This applies to both. `plan` owns the step. |
| <a id="r-22"></a>R-22 | When setup and pipeline run | `plan` invokes `project-setup` when the Makefile is missing, or when the slice adds or overrides a target. It does not invoke `project-setup` otherwise. `release` invokes `github-pipeline` when the change touches the workflow, the version, publish, the image, cleanup, or retention. `release` invokes `project-setup` only when that same delivery change adds or overrides a Make target. `release` does not call `project-setup` on every ship. When the task does not ship, the Release section is `Not invoked: this slice does not ship.` [R-57](#r-57) says how a slice ships. This applies to a product repository. `plan` and `release` own the invocations. |
| <a id="r-59"></a>R-59 | A slice that starts at develop | A request that names a source file, a failing test, or a known issue starts at `develop`. A fix is such a request. When no history file exists for the task, `develop` creates the branch of the slice and asks `record` for a history id. `record` writes the file from its template and adds one roadmap line with that id. The Plan section is then one sentence that says why `plan` was not invoked. The slice then goes through `review` and `release` as every slice does. This applies to both. `develop` owns the request. `record` owns the file. |
| <a id="r-57"></a>R-57 | Release ships the slice | `release` ships a reviewed slice. It stops when `make lint` or `make test` failed or did not run, or when a finding is neither fixed nor a known-issue id. `release` asks the owner before the ship when the request did not ask for one. When the owner merges later, `release` does every step before the merge, and the pushed branch is closed on the board. The slice is one branch. `release` commits the change and pushes the branch. The first line of a commit message is one sentence that says what the system now does. CI runs the same Make targets on that push. `release` runs `make ci-status WAIT=1`, and it stops when the target fails, because the run failed, did not finish, or does not exist. A repository with no workflow runs `make editorconfig`, `make format`, `make lint`, `make test`, `make integration`, and `make coverage` on the machine instead. When the gates passed, `release` writes the Release section, asks `record` to close the task, and commits the board documents on the same branch, so the board is correct on the default branch after the merge. Then `release` merges the branch into the default branch and pushes the default branch. If `.github/workflows` exists and `make help` lists `pull-request`, `release` runs `make pull-request` and `make pull-request-merge WAIT=1`. If not, it makes a Git merge commit. The general rules say that the owner creates a `v*` tag and a skill creates none. A push to the default branch publishes when `github-pipeline` is installed. A shipment is a binary, a container image, or a library package. A Make-only repository then runs the target its `CLAUDE.md` names, such as `make build` for a library package. A library with no package ships with the merge. This applies to a product repository, and to this collection without the publish. `release` owns the steps. |

## Documents

| Id | Title | Statement |
| --- | --- | --- |
| <a id="r-24"></a>R-24 | Product document homes | A product repository keeps six homes, and `record` is the only writer. In-progress work is one line in `docs/ROADMAP.md`, ids only, citing a history id and, when there is one, a proposal id. The line has no grill. A defect is a table row in `docs/KNOWN_ISSUES.md`, with an id of `K-` plus a number. Delete that row when the fix lands, then retire the id. A small choice is a table row in `docs/DECISIONS.md`, with an id of `D-` plus a number. Its status is Open or Decided. There is no settled-since table. A Decided entry is one sentence. An architecture or development rule is `docs/adr/<id>.md`, with an id of `ADR-` plus four digits. Work that is not started is `docs/proposals/<id>.md`, with an id of `P-` plus a number. That folder is the backlog. A started slice is one file `docs/history/<id>.md`, with an id of `H-` plus the date and a slug. `plan` reads these before it asks. This applies to a product repository. `record` owns the files. |
| <a id="r-67"></a>R-67 | Board templates | `record` has one template for each board document in `templates/`: `ROADMAP.md`, `KNOWN_ISSUES.md`, `DECISIONS.md`, `adr.md`, `proposal.md`, and `history.md`. `record` copies the template at the first write and keeps its layout. A decision and a known issue are table rows. The first ids are `D-1`, `K-1`, `P-1`, and `ADR-0001`. A history id is `H-` plus the date and a slug, as `H-2026-11-20-slugify`, and the branch of the slice has the slug as its name. An ADR, a proposal, and a history file have a frontmatter block. A list in the frontmatter is on one line. The scripts of `record` and `project-report` read these layouts and no other. `record` adds one roadmap line when it creates a history file. A roadmap line starts with `- `. The next number of a kind is one above the highest number of that kind in the documents and in `docs/ids.yaml`. In an ADR, `skills` names installed skills. A rule for every change names `develop` and `review`. This applies to a product repository. `record` owns the templates. |
| <a id="r-15"></a>R-15 | Product roadmap and ADR | A product repository keeps in-progress work in `docs/ROADMAP.md` and a rule in `docs/adr/`. The skills still teach that board. Do not remove the ADR, roadmap, and decision machinery that other projects install. When a repository has ADR files, `make toon` and `make project-report` keep that product behaviour. This applies to a product repository. `record` owns the roadmap line and the ADR. `plan` and `migrate-docs` name both paths. |
| <a id="r-53"></a>R-53 | Costly choice becomes an ADR | In a product repository, when the owner answers a choice that is expensive to reverse, `plan` asks `record` for an ADR id. `record` writes `docs/adr/<id>.md` with the status `Accepted`. The Plan section cites that id. A choice that is cheap to reverse stays a Decided entry. When the repository keeps `docs/REQUIREMENTS.md` and does not keep `docs/adr/`, the answer is a row in that list. `plan` owns the request. `record` owns the write. |
| <a id="r-54"></a>R-54 | Stages read the accepted ADRs | `develop` runs `make toon` and reads `docs/adr/index.toon` before it edits. A change that breaks an accepted ADR is a finding. A repository that keeps `docs/REQUIREMENTS.md` and no `docs/adr/` reads `docs/requirements-index.toon` in these steps, as the general rules say. A row of that list takes the place of an ADR: `develop` stops when the change would break a row, and `review` writes a finding. This applies to a product repository. `develop` and `review` own the read. |
| <a id="r-55"></a>R-55 | An ADR may replace a skill rule | An accepted ADR replaces a skill rule only when the ADR is a divergence. A divergence names the rule, what differs, and why. An ADR that differs from a skill rule and does not name these three is a finding in `review`. What `github-pipeline` says is not a divergence stays not allowed. A pipeline divergence is written where `github-pipeline` says. Every other divergence is an ADR. This applies to a product repository. `record` owns the rule. `review` owns the check. |
| <a id="r-56"></a>R-56 | ADR status and replacement | `record` owns the ADR status. The values are `Accepted` and `Superseded`. A new ADR names the ADR it replaces in `supersedes`. `record` then sets the status of the replaced ADR to `Superseded`. `plan`, `develop`, and `review` follow only an accepted ADR. The project report does not list a superseded ADR as an id with no test. This applies to a product repository. `record` owns the status. |
| <a id="r-61"></a>R-61 | ADR body | An ADR body has the section `## Rule` and the section `## Why`. Rule is what an agent must do or must not do, in sentences `review` can check. Why is the reason, and the options that were not chosen. An ADR that replaces a skill rule also has the section `## Divergence`. An ADR is short. It does not copy the grill. This applies to a product repository. `record` owns the sections. |
| <a id="r-62"></a>R-62 | Decision log | `make decision-log` writes `build/decision-log.md`. It is the document a person reads. It lists each accepted ADR with its rule, its reason, and the skills it names. It lists each Decided entry, each Open entry, and each superseded ADR with the ADR that replaced it. A repository that keeps `docs/REQUIREMENTS.md` and has no ADR file gets that list in the log. Hand-editing the log is a defect. A repository that renders docs uses this file as a source. The log does not replace the ADR an agent opens. This applies to both. `record` owns the target. |
| <a id="r-25"></a>R-25 | One home for the grill | A proposal means the work has not started. A roadmap line means in-progress ids. A history file means a slice that has started. Do not copy a grill into all three. A slice that starts at `develop` gets its history file as [R-59](#r-59) says. Implement now: `plan` asks `record` for a history id, writes the questions and answers in Plan, including the boundary and the pattern, and sets Develop, Review, and Release to `Not invoked yet.` Do not copy the grill into the roadmap. Implement later: `plan` asks `record` for a proposal id and writes `docs/proposals/<id>.md`. Do not create a history file. Do not add a roadmap line. When a proposal is picked up, `record` creates the history file, sets `proposals:` to that id, sets the proposal status to `started`, and adds one roadmap line with both ids. The Plan section cites the proposal id. Develop does not copy the proposal. This applies to a product repository. `plan` and `record` own the choice of home. |
| <a id="r-26"></a>R-26 | Four history sections | Every history file has the headings Plan, Develop, Review, and Release. `record` rejects a file that is missing one. `plan` creates the file when implementation starts, or `develop` asks for it as [R-59](#r-59) says. The status of a history file is `started` or `closed`. Later stages append. A stage that did not run gets one sentence. Plan holds the questions and answers when `plan` ran. Develop holds what changed and which language skill was used. While the task is open and `develop` has not run, Develop is `Not invoked yet.` When the task closes or waits, that section is one sentence. Review holds the gates, the subskill results, the findings, and what was left alone. A subskill that is not installed is one line, such as `security: not installed`. Release holds what shipped, or `Not invoked: this slice does not ship.`, or `Not invoked yet.` An agent on another task opens a history file only when an id names it. This applies to a product repository. `record` owns the headings. Each stage owns its section. |
| <a id="r-58"></a>R-58 | Closing a task | `release` asks `record` to close the task, when the slice shipped and when it does not ship. A task whose work waits stays open. A slice that is done and waits only for the merge of the owner is closed on its branch. `record` stops when the Plan, the Develop, or the Review section of the history file is still `Not invoked yet.` `release` writes the Release section before it asks for the close. It sets the history status to `closed`. It deletes the roadmap line that cites the history id. It sets the status of the proposal to `done`. The status of a proposal is `open`, `started`, or `done`. It deletes the row of a fixed known issue and retires that id. It stops when a test still names that id. An ADR and a Decided entry stay in force. In a repository that keeps `docs/REQUIREMENTS.md` and does not keep `docs/ROADMAP.md`, `record` deletes the Open row for the task and retires its id. This applies to both. `record` owns the steps. |
| <a id="r-27"></a>R-27 | Links are id keys | An ADR, a decision, a proposal, and a history file name other documents by id. The YAML keys are `id`, `title`, `status`, `adrs`, `skills`, `decisions`, `proposals`, `issues`, and `supersedes`. The key `relates:` is not used. An id in a path fails `review`. This applies to a product repository. `record` owns the keys. This collection's decision list is a table, as [R-28](#r-28) says, and does not use this YAML block. |
| <a id="r-69"></a>R-69 | Ids are links | In running text of a document under `docs/`, each id is a link to its item, so a person goes from one item to the other with one click. `make links` writes the links. An agent writes the plain id and runs the target. A table row gets an anchor in its id cell, and the anchor is the id in lowercase. An id of a table row links to that row. An id of an ADR, a proposal, or a history file links to that file. A retired id has no target and stays plain text. An id in a code span, a code block, a heading, the frontmatter, or the id cell of a table stays plain text. `make links` changes nothing when it runs a second time. `make links-check` fails when an id in running text is not a link, when a link is wrong, or when a row has no anchor. `review` runs it. The scripts that read a table id ignore the anchor. `make decision-log` and `make project-report` give each item an anchor and link each id, with a path from `build/`. This applies to both. `record` owns the two targets. |
| <a id="r-70"></a>R-70 | Onboard | `onboard` brings a project onto this collection when the owner says `report and integrate`, for a new project and for an existing one. It is the order of the other skills and does no work that they own. It checks that Make, Git, and Podman run, reads the language, the old board, the remote, and the tests, and asks only what the files do not tell, such as how the project ships. If `CLAUDE.md` is missing or has no general rules, it reads the entry-file template first. It stops when a gate fails. It writes no feature and opens no history file. Its commits go on the default branch, and it pushes only to the remote the project already has. This applies to a product repository. `onboard` owns the order. |
| <a id="r-71"></a>R-71 | Shared contract targets | `project-setup` has `contract.mk` with the targets of the Make contract. `project.mk` and the `sdlc.mk` of `github-pipeline` both include it, so a project that switches from `project.mk` to `sdlc.mk` keeps `setup`, `build`, `test`, `format`, `lint`, and `coverage`. This applies to a product repository. `project-setup` owns `contract.mk`. `github-pipeline` owns the rest. |
| <a id="r-72"></a>R-72 | Update path and version tags | The README states how a project takes a new version of this collection: set `ref` to a `vMAJOR.MINOR.PATCH` tag, run `make skills-update`, run `make toon` and `make links`, run the gates, and commit `.claude/skills/`, `apm.yml`, and `apm.lock.yaml` together. `onboard` names the pin to the owner when a tag exists. This collection tags its releases with `vMAJOR.MINOR.PATCH`, and the owner creates the tag. This applies to a product repository. The README owns the text. |
| <a id="r-73"></a>R-73 | Doctor and src layout | `make doctor` checks GNU Make 3.81 or newer, Git, and `podman info`, and, when the project has a workflow, the remote `origin`. It prints `ok` or `FAIL` with the fix, and it stops on a `FAIL`. `doctor.mk` makes `doctor` the first prerequisite of `setup`. `make setup` therefore runs `doctor` before `toon` and before its recipe, also in the Node and Gradle templates. A unit test checks the prerequisite and the order of the includes.
